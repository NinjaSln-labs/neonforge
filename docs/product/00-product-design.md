## 一、产品定义

### 1.1 这是什么

NeonForge 是为 DeepSeek 打造的 **AI 问题工作台**：用户用自然对话说出"当前的问题"，NeonForge 通过内在的工程/设计/编排自动推进，交付解决结果。

**用户流**：`说出问题 → 分析 → 目标/方案确认（方案卡——文件+假设+验证计划）→ 分步授权执行 → 解决确认（证据对账——交付≠解决）→ 交付结果（数字产物/修复闭环）→ 反馈 + 指导继续`

- **能力边界**：一切能被数字工具解决的直接解决；超出（域名/备案/线下履约）→ 交付数字产物 + 分步指导，**不装能**
- **不是**：IDE（编辑器为中心）、Chatbot（只聊不交付）、多模型客户端

### 1.2 核心原则（所有设计决策的源头）

1. **帮用户解决当前的问题。** 一切围绕"问题被解决"（问题关闭），不是"我给你写了代码"。
2. **分步授权，每一步可控。** 分析（只读）自动；写入/执行/部署逐级授权（信任阶梯 L1-L4）；可随时撤销。
3. **交付可验证。** DoD 前置（动手前对齐"什么叫解决"+ 验收标准）（DoD 对齐 ⏸ V2——2026-08-15 裁决；V1 以解决确认卡（证据对账）+交付包为可验证闭环）、证据链（做了什么/怎么验）、失败可恢复（失败包/备份/回滚/半成品可带走）。
4. **不装能。** 超出数字能力 → 明说 + 给产物 + 分步指导；不静默失败、不假装搞定。
5. **上手不学。** 零学习成本：说出问题就会被解决；不学指令/不学 IDE/不注册。
6. **安静可信。** 不打扰、不炫技；过程可见但不说术语；本地优先、数据出域显式。

**原则 → 设计映射表**

| 原则       | 落地设计（§对应）                                                                                                                            | 反例（违规即缺陷）                                |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| 1 解决问题 | 问题台账/交付包（§3.3）、DoD 前置验收（§4.1）、北极星=问题关闭率+二次委托率                                                                  | 交付"我写了代码"而非"问题已解决可验证"；交付≠关闭 |
| 2 分步授权 | 信任阶梯（§4.2）、写入模型（§3.5 接受=暂存/写入=原子 apply）、可撤销                                                                         | 未授权写盘/部署；授权疲劳（步步弹窗）；无撤销     |
| 3 可验证   | DoD 对齐（§4.1——DoD 对齐 ⏸ V2——2026-08-15 裁决；V1 以解决确认卡（证据对账）+交付包为可验证闭环）、证据链（diff/日志/前后对照）、失败包（§5） | 只报"已完成"无证据；失败不说明影响/下一步         |
| 4 不装能   | 边界承诺（§1.3）、外部世界协调（§4.4：等待清单+触发条件+指导）                                                                               | 假装搞定域名/备案/线下；硬做做不了的事            |
| 5 上手不学 | 场景卡片（§3.2）、非技术视图（§3.8）、人话交付                                                                                               | 首次强制教程；核心依赖快捷键/术语                 |
| 6 安静可信 | 非模态提示条、数据出域清单（§10）、本地优先                                                                                                  | 弹窗打扰；隐式上传；面向用户抛技术术语            |

**原则间冲突裁决**：

| 冲突                                                       | 裁决                                                                                                 |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 「2 分步授权」vs「5 上手不学」（非技术想一键 vs 每步确认） | 信任阶梯 + 非技术视图主路径「接受并写入」（改动说明先行，可一键）；高风险操作（删/部署）永远单独确认 |
| 「3 可验证」vs「6 安静」（证据 vs 不打扰）                 | 证据折叠在交付包内（人话摘要 + 详情展开），非模态                                                    |

### 1.3 能力边界与首次使用

**能力边界（不装能）**：

- 数字工具能力内：直接解决（文件整理/数据加工/建网站源码/修系统/做小工具/0-1 交付）
- 超出数字能力（域名/备案/线下/法律）：交付数字产物 + 分步指导——明说"我做到哪、你必须做哪"

**首次使用前提**：需要 DeepSeek 兼容 API Key（模型为 DeepSeek V4 系列；接入方：DeepSeek 官方 / Command Code / OpenCode Zen / OpenCode Go——ADR-010）。首次打开：

- 本地已有有效 Key：自动检测，直接进入启动页
- 没有：简洁配置页（选接入方 → 粘贴 Key → 验证 → 进入）
- 网络不通：提示 + [跳过（离线不可用）]

零学习成本指不学 IDE 操作，不是零依赖。

### 1.4 用户

两类用户，一套内核、双视图（同源状态，可切换）：

- **不会写代码的人（V1 主）** — 说出问题 → 被解决：交付数字产物（文件/源码/小工具）+ 人话说明 + 指导。看「非技术视图」（产物/预览/验收清单），不暴露术语。
- **会写代码的开发者** — 授权闭环：异常修复（定位→方案→修复→测试→部署→复核→反馈）/ 0-1 交付（软件工程模型/敏捷）。可展开技术细节、可手动编辑（编辑器=可选能力）。

### 3.5 Diff 审核

**默认审核模式（修复审计 M5）：**

用户点待审核任务或搭档改完后：

1. **先展示改动摘要**：哪些文件、几处改动、每处简述
2. 底部按钮：主按钮「全部接受并写入」、次按钮「逐处审查」
3. 用户点逐处审查 → 进入逐处模式（同原规格）

**写入时机（修复审计 M3）：**

- 逐处点 ✓ 接受 = 暂存（标记为已确认，不写文件）
- 点「全部接受并写入」或逐处审完点「写入文件」= 一次性原子 apply
- 状态栏显示「待审核: N」→ 接受后「已暂存: N」→ 写入后清零

**全部接受确认（修复审计 M1）：**

不用弹窗。diff 视图中出现确认提示条：

```
┌──────────────────────────────────────────────┐
│  确认写入全部 4 处改动？                        │
│  [写入] [取消]                                 │
└──────────────────────────────────────────────┘
```

提示条在编辑器底部，不遮挡，不模态。

**完成状态：**

```
✅ 改动已写入文件。
```

无 🎉，无庆祝动画。

## 四、交互模式

### 4.1 问题闭环流（v2 重定义）

```
说出问题（对话入口，零学习成本）
  → 分析（只读自动 · L1）→ DoD 对齐（"什么叫解决"+ 验收标准，用用户的话）（DoD 对齐 ⏸ V2——2026-08-15 裁决；V1 以解决确认卡（证据对账）+交付包为可验证闭环）
  → 方案确认（方案卡——文件清单+假设+验证计划，批准/修改/重出）→ 执行（L3 分步授权）
  → 交付包（产物 + 做了什么 + 验收对照 + 下一步/复跑入口）
  → 用户确认问题关闭（交付 ≠ 解决，以关闭为终态；解决确认=声明+证据对账——证据不足不弹卡）
  → 超出数字能力部分：产物 + 分步指导（不装能）
```

**确认卡（结构化确认——2026-08-07 无阶段定论；2026-08-16 触发权升级）**：需要用户决定的点（目标确认/方案确认/解决确认/工具授权）→ 对话内嵌**确认/拒绝卡片**——卡弹出 = **会话进入 PENDING（等用户决策）**——用户不决策则模型任何动作都无效（做了白做）——用户「是」→ 推进 /「否（带原因）」→ 调整。**触发权在系统**（决策点=状态×提议×动作属性的确定性派生——模型只能提议不能制造卡；方案卡=可审阅 PlanProposal，解决卡=证据对账）——对齐竞品：Claude Code/Gemini Plan 门、Cline Plan/Act。

- 每一步可暂停/撤销/回滚（失败包 + 备份 + 半成品可带走）
- 开发者场景（异常修复/0-1 交付）：同内核 + 部署授权（L4：备份→热更新→复核→反馈）

### 4.2 信任阶梯与状态变化表

**信任阶梯（L1-L4，渐进解锁，进度可见）：**

| 等级    | 能力                   | 授权                   | 典型               |
| ------- | ---------------------- | ---------------------- | ------------------ |
| L1 观察 | 只读分析/草稿/本地整理 | 首次全局授权，静默     | 分析问题、生成预览 |
| L2 建议 | 生成方案/补丁          | 建议呈现，一键应用     | 方案确认、PR       |
| L3 操作 | 写文件/执行/网络       | 分步授权 + 快照        | 修改文件、跑命令   |
| L4 委托 | 高度信任重复任务       | 用户设规则，可降级撤销 | 格式化类自动应用   |

**问题状态机：**

| 状态       | 说明                                                                                                 | 用户下一步                                                                            |
| ---------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 理解中     | 分析问题、DoD 对齐（DoD 对齐 ⏸ V2——2026-08-15 裁决；V1 以解决确认卡（证据对账）+交付包为可验证闭环） | 补充/确认验收标准                                                                     |
| 方案待确认 | 方案卡（PlanProposal——文件清单+假设+验证计划）                                                       | [批准并执行] / [修改方案（带原因）] / [重出]                                          |

| 失败可恢复 | 失败包 + 回滚点                                                                                      | 重试/换方案/人工接管                                                                  |

### 4.3 交付包（交付即闭环）

每个问题交付时产出**交付包**：

- 产物（文件/源码/修复摘要/数据）
- 做了什么（人话摘要）
- 验收对照（对 DoD 逐项打勾：怎么验/不对点哪里）
- 下一步 / 复跑入口（「上次那个再跑一遍」= 一等操作）
- 超出部分指导（数字能力外：分步指引）

### 4.4 外部世界协调（不装能落地）

- 明确建模「数字工具做不了但任务需要」的节点：域名/备案/第三方平台/线下履约
- 交付「等待清单 + 触发条件 + 你操作时的一键继续」，不假装已搞定

### 4.5 对话回合礼仪（谁在什么时候开口）

> 2026-10-04 新落节（ADR-018）。本节只定**用户可观测契约**——即"用户看得见什么、看得见意味着什么"。轮次归属的领域建模（Turn 实体、身份 doctrine、驱动权拓扑）**下放阶段 C**；`00-domain-authority §3.2` 作为不变量 1 唯一措辞源的地位不因本节改变（ADR-015 #8 继续有效）。
>
> 立节约束（ADR-016 规则 1）：本节引入的**开口权 / 系统轮披露条 / 排队中徽标**均为**呈现与对话语义概念**，其权威域＝产品呈现层，不落领域状态字段——故不逐条出域归属卡；一旦阶段 C 要把它们做成 `ConversationState` 成员，须回到 ADR-016 补卡。

**C1 发言真实性**——用户气泡只能由用户的真实发言产生。搭档与系统**不得为驱动自身而伪造用户发言**（按钮回声不是发言）。推论：用户决策一经卡片落定，**下一句由搭档开口**；搭档确需向模型转述该决策时，走"搭档侧的自述/系统轮"（C4），不走用户气泡。

**C2 意图变更须显式**——改变意图/换目标是**第二条决策通道**（延续 ADR-006），但**不得由措辞匹配推断**。产品呈现要求：活卡存续期间，卡上必须有显式出口（"改说新方向"级动作），用户经它产生的答复是结构化决策记录；用户在同一期间**直接打字**发送的文本按补充信息处理。产品承诺：**用户打的字不会被静默解释成"拒绝"。**

> 与领域权威的分歧：`intent-confirmation-domain-design.md:215` 现授权 C2 词表分流承担此通道。本契约不废"打字可换目标"（ADR-006 完整保留），只要求该通道**显式化**；`isConfirmIntent` 词表作为决策入口的资格由本契约收回。

> **提示词侧同源（对标批补）**：`src/renderer/sysPrompt.ts` 规则 ⑳ 早已逐字规定「**确认只能通过界面确认卡按钮完成**：用户文本回复永远不构成结构化确认——严禁要求用户『输入特定文字/暗号』来确认」。C2 是对 ⑳ 的产品化接管，不是新方向；**实现不得反过来依赖词表去兑现 ⑳**（词表的存在本身就是 ⑳ 被绕过的证据）。

**C3 输入不静默消失**——用户发送即上屏，搭档忙碌时同样上屏并带"排队中"标（与 §3.6 任务队列的 `○ 排队中` 同一徽标语言），当前回合收口后自动转发。排队区**按条可见、可撤回（取回输入框）、可编辑、可重排**；任何"入队后被后发条目顶掉且用户无感知"的实现形态判为产品缺陷（对齐 `02 §4.12` 排队衔接 + ADR-013）。

**C4 系统自发轮可解释**——系统自发的模型轮（催推进、对账引导、卡住后的显式恢复打断）必须在对话流留一条**折叠的披露条**：一行人话说明"为什么搭档又开口了"+ 可展开**原因与触发依据**（展开的是"为什么"，不倾倒逐字内部提示词）+ 无用户气泡、无 `message_sent`（通道语义仍遵 ADR-013 与 `02 §4.12` 的 silent 定义，本节只补**呈现义务**）。理由：无披露条时，用户与测试看到的都是"消息凭空出现/幽灵占位"，二者不可区分。

**C5 等待必须有可见归宿**——任何"搭档正在处理"的呈现，必须对应一条真实的在飞请求；请求终结（正常收口 / 零产出 / 失败 / 被打断）时，该呈现必须收口。**"处理中"不得成为无主状态**。

**C6 决策点有生命终点**——卡不会永远活着，也不会永远能点：

- **跨重启/重连后旧卡不可批**——用户离开再回来，面前必须是重新提出的决策点；旧实例只可读、不可决（呈现为"已过期"而非静默消失）。
- **断线期间待决不丢**——决策内容随会话存续，回来按上一条处理。
- **卡不因时间自动消失**——自动消失＝把"用户没空答"读成"用户拒了"，属误杀。超时解算只在**授权面**按 ADR-017 的 TTL/expired 语义进行；确认卡族无自动超时。
- 取舍注明：竞品有"审批超时自动拒"的路线（Cline/Codex），本条有意不采——本产品把拒绝设计成必须带 `RejectReason`（§4.1 C2 值对象），自动超时给不出原因，只能落"过期不可批＋重出"。

**C7 用户输入有三态投递时机**——「发出去」≠「现在生效」。产品定义：**排队**（当前回合收口后自动发出——V1 默认）/ **显式打断**（停止按钮 `Esc`，见 §六）/ **转向**（在下一个工具边界插入，保留已完成工作——**V1 不做**，标为 V1.5，须与 §3.6 串行队列一并设计）。任何一态都不得丢弃输入（C3 是底线）。

**C8 拒绝必须带方向投递**——用户「否」不是一次静默的关闭：`RejectReason`（方向/范围/复杂度/缺信息/修改/其他）必须①交给模型调整、②在对话流可见（"已把你的原因转给搭档"级别的回执）。**拒绝无回执＝产品缺陷**（对齐 §4.1 三确认点的"带原因"承诺——原因不能只停在事件里）。

**C9 打断保留残值**——被打断的回合**已完成的工作不消失**：已写入的文件、已产出的部分内容、已跑过的验证都保留并可查；打断只冻结"接下来"，不撤销"已经"。回滚是另一件独立的事（快照回滚 §4.9），不得与打断混为一谈。

**C10 一条消息有四个状态**——发送不是瞬间成功：`已输入 → 已提交 → 已消费（真正进入这一轮）→ 失败`，四态对用户可区分。硬规矩：① **提交成功≠被消费**，不得把"已提交"呈现成"搭档已经收到了"；② **失败不得静默自动重发**，须给出可重试/可撤回的出口。本条同时是**取证义务**——nudge 死信、迟到文本没送到、请求被外部网络变更打断，都属 C10 未兑现。

**C11 搭档忘事必须可见**——上下文压缩/截断发生时，对话流须有轻量标注（"较早的对话已压缩为摘要"级别），且压缩**不得静默移除活卡的决策内容**。理由：忘事不可见时，用户会把"搭档忘了"误读成"搭档不听话"，进而给出虚假的负反馈（与 §3.9 上下文控制衔接）。

**C12 输入必须落到确定的任务**——§3.6 串行队列下，用户输入**始终归属当前正在执行的会话**；未来放开并发（V2 多 Agent/Worktree）时，"这条消息发往哪个任务"必须先有显式选择机制才允许并发。**不得出现"消息发出去了，但进不到我正在看的那个任务"**。

- Inline 代码补全

- Git GUI

- Web 版
- 浅色主题
