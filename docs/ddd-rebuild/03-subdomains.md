## 3. 核心域声明

### 3.1 核心域 A：任务决策与证据核验（Task Decision & Evidence Verification）

**为什么是核心**

- 它定义了产品与用户的“协作契约”：模型只能提议，用户必须确认；模型声称完成，系统必须核验。
- 它把“AI 能不能做事”转化为“用户能否可控地得到一个可核验的结果”，这是非技术用户愿意使用的前提。
- 代码中的 8 条不变量、证据门、loop guard、forced clarify、progress guarantee 都集中在这里。

**边界**

- 包含：目标/方案/解决三阶段决策点、单一 PENDING、拒绝原因、完成证据核验、planned/produced 对账、无进展对话保护、推进保障。
- 不包含：具体工具执行、文件系统、Provider 传输、UI 渲染。它只消费“提议”和“动作属性”，不直接执行副作用。

**衡量指标**

| 指标 | 定义 | 目标方向 |
| :--- | :--- | :--- |
| 决策转化率 | 确认 goal → 确认 plan → 确认 resolution 的完成比例 | 上升 |
| 证据门拦截率 | 完成声明被 `verifyCompletion` 拒绝的比例 | 观测（过高说明模型证据能力差） |
| 证据通过率 | 系统代跑 + planned 覆盖通过的比例 | 上升 |
| 决策点往返轮次 | 同一决策点从提议到确认的轮次 | 下降 |
| 循环保护触发率 | loop-guard / forced-clarify / needs-human 次数 | 观测（过高说明模型或提示词退化） |
| 任务边界重置正确率 | 新目标确认后计划/产出/拒绝记忆清零 | 100% |

**风险**

- 模型格式漂移导致决策点不弹卡；已有协议工具 + 文本降级 + 参数校验。
- 用户文本确认与结构化确认的语义冲突；见 08。
- 历史命名（execution/achievement）与领域语义（plan/resolution）不一致；见 08。

**演进方向**

- 把决策点与证据核验抽成可独立测试的“协作协议”包；为未来多 Agent/多任务队列复用。
- 引入决策点版本与事件 schema 版本，支持回放与 A/B 提示词。

### 3.2 核心域 B：受控执行与信任阶梯（Trusted Execution & Trust Ladder）

**为什么是核心**

- 目标用户非技术，无法判断命令/文件操作的风险；产品必须把“权限”产品化，而不是把终端弹窗丢给用户。
- 授权疲劳与安全边界是竞品（Claude/Codex/Cursor）都在解决的核心体验问题；本产品用 L1-L4 信任阶梯、允许并记住、低危委托、快照回滚来差异化。

**边界**

- 包含：工具风险分级、规则引擎、动作属性判定、沙箱路径、逐次授权、拒绝记忆、写前快照、回滚、进程取消。
- 不包含：模型决策（属于核心域 A）、具体 Provider 传输（属于 Supporting）、UI 样式（属于应用层）。

**衡量指标**

| 指标 | 定义 | 目标方向 |
| :--- | :--- | :--- |
| 未授权副作用次数 | 未经用户批准的 write/edit/bash 执行次数 | 0 |
| 授权卡密度 | 每个任务弹出的授权卡数量 | 下降（在安全前提下） |
| 回滚成功率 | 用户点回滚后文件恢复原样比例 | 100% |
| 拒绝记忆命中率 | 拒绝后同类动作被短封的比例 | 上升 |
| L4 委托误放行 | 低危委托下发生的非预期写入 | 0 |
| 进程残留 | 应用退出后残留的 bash/dev server 进程 | 0 |

**风险**

- 只读判定启发式被绕过（`sed -i`、`find -exec`、`awk system()`、`git branch -D` 等）；见 08 安全发现。
- `read` 绝对路径无沙箱，可能读取敏感文件并发送给模型。
- 软沙箱不是 OS 隔离；需要明确用户预期。

**演进方向**

- 将动作属性判定升级为“命令 AST/参数级”分析，而不是字符串前缀。
- 引入文件路径 realpath 解析，防符号链接逃逸。
- 将 L4 委托从 localStorage 开关升级为按工具/路径/风险的可视化规则。

## 4. 所有权建议

当前是单产品团队、单仓库；所有权按 **模块职责** 而不是独立团队划分。以下“Owner”指该能力的代码与语义负责人。

| 能力/子域 | 建议 Owner | 依赖方 | 协作方式 |
| :--- | :--- | :--- | :--- |
| 决策与证据核验（Core A） | 领域/产品 + 应用层 | Provider、工具执行、UI | 领域不变量评审 + 单测门禁；提示词与协议工具共同演进 |
| 受控执行与信任（Core B） | 执行层/安全 + 应用层 | 工作区、环境、平台 | 安全评审；授权 UX 与规则引擎联合设计 |
| 工作区与环境 | 执行层 | 决策核验、工具执行、交付 | 环境单源；路径/端口/进程契约 |
| 交付与问题台账 | 应用层 + 产品 | 工具执行、工作区、决策核验 | 交付真实性评审；演示面板与生产路径分离 |
| 模型接入 | 执行层/平台 | 配置、会话、上下文 | Provider descriptor 契约；SSE/重试/修复测试 |
| 时间线与可观测 | 平台 | 全部上下文 | 事件 schema 注册；日志失败可见性 |
| 配置与凭据 | 平台/安全 | Provider、Web 工具 | 密钥存储评审；最小权限 |
| 上下文与检索 | 执行层 | 工作区、Provider | 注入确定性；LSP/RAG 降级 |
| 平台与插件 | 平台 | 全部 | 生命周期/清理；插件占位明确标注 |
| 变更与版本 | 执行层 + 应用层 | 交付、工具执行、工作区 | 变更集契约；基线/回滚测试 |
| 任务编排 | 应用层 | 会话与任务、UI | 调度策略；阻塞/取消与 Task 状态事件对齐 |
| 用量与成本 | 平台/财务口径 | Provider、UI、审计 | usage 字段契约；价格表版本化 |
| 扩展与集成 | 平台/安全 | 工具执行、配置 | 扩展信任模型；MCP 能力描述 |
| 验收与质量门禁 | 领域/产品 | 交付、方案、完成核验 | 验收来源与证据绑定；门禁判定单源 |

### 4.1 跨团队/跨组织协作点（至少 3 个）

1. **模型供应商**（DeepSeek / Command Code / OpenCode）：API 兼容性、模型命名、区域限制、速率限制、错误码语义。协作方式：Provider descriptor + 兼容性测试。
2. **操作系统与运行时工具链**（macOS/Windows/Linux、node/python、包管理器）：能力检测、命令差异、进程组语义、路径大小写。协作方式：`check-capability` + 平台能力表。
3. **Web 检索供应商**（DuckDuckGo / Keenable / 用户自有端点）：可达性、配额、结果格式、公共试用限制。协作方式：web access probe + 降级。
4. **安全/隐私评审**：数据外发、密钥存储、沙箱边界、命令执行。协作方式：威胁建模 + 安全测试用例。
