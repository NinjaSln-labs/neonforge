## 审计项

### 1. 确认点完整性（通过）

| 确认点 | 设计 | 状态 |
|--------|------|------|
| GoalConfirmed | 用户确认目标（确认/重新描述）——未确认只澄清 | ✓ |
| ExecutionConfirmed | 用户确认执行（确认/修改方案）——未确认不动手 | ✓ |
| AchievementConfirmed | 用户确认解决（已解决/还要改）——未确认不收敛 | ✓ |

**Major 1 ✅ 已闭合（00 §3.4）**：执行确认的活动边界工具级清单——未确认执行时 read/search/LSP/check-capability/plan_approval 放行（信息类）、write/edit/bash 挂起（执行类——pending 等确认执行卡）。

### 2. 推进门控（通过）

确认点未确认 → 模型停在该确认点（结构性——非拦截）。状态机：clarifying → goal-confirmed → executing → achieved-reported → resolved。

### 3. 执行保障（通过）

| 规则 | 设计 |
|------|------|
| 确认后无产出 | forceTool=true（required——防只说不做）|
| 工具失败 | 释放（auto——模型诊断修正——required 压制诊断是反模式）|
| 计划写完 | 释放（模型可收敛——写 1 文件 ≠ 任务达成）|
| 达成确认 | 释放（用户确认解决——对话收敛）|

### 4. 宿主强制边界（通过）

计划清单（追加语义/显式可见/拒绝带边界）——模型漂移防护（行业共识）。

**Major 2 ✅ 已闭合（00 §3.5 + 05 §4）**：门控优先级显式——执行确认是执行级边界（先判定——未确认则全部执行动作挂起，不管清单）；计划清单是文件级边界（后判定——已确认执行后逐文件核对——拒绝带边界）。两个边界不互斥。

### 5. 能力环境（通过）

环境=事实来源（一次检测）→ 能力=语义视图（推导）——Ledger 回填（自学习）——环境快照注入模型。

### 6. 结构化确认（通过）

确认卡（确认/拒绝按钮）——对齐 OpenHands USER_CONFIRMED/USER_REJECTED、Cline allow/always/reject。

**Minor 1**：拒绝动作的后续语义——「重新描述/修改方案/还要改」是拒绝后的引导——应标准化（拒绝 → 模型收到拒绝事件 → 重试/调整）。

### 7. 时间线（通过）

全步骤统一记录（JSONL）——崩溃保留已写行。

**Minor 2**：时间线事件类型与确认点事件（goal/execution/achievement confirmed+rejected）应完整（当前已列）。

**Minor 3**：多会话隔离（session 字段）——跨进程 seq 冲突（进程内自增）——需全局唯一（ts+进程 id）。
