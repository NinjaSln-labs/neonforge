## 一、产品定义

### 1.1 这是什么

NeonForge 是 **AI 问题工作台**（唯一定义处＝`08-product-master-anchors §3.1`；**provider 不入定位句**——模型选型属 §1 策略层且可切换，ADR-007/010）：用户用自然对话说出"当前的问题"，NeonForge 通过内在的工程/设计/编排自动推进，交付解决结果。

**用户流**：`说出问题 → 分析 → 目标/方案确认（方案卡——文件+假设+验证计划）→ 分步授权执行 → 解决确认（证据对账——交付≠解决）→ 交付结果（数字产物/修复闭环）→ 反馈 + 指导继续`

- **能力边界**：一切能被数字工具解决的直接解决；超出（域名/备案/线下履约）→ 交付数字产物 + 分步指导，**不装能**
- **不是**：IDE（编辑器为中心）、Chatbot（只聊不交付）、多模型客户端

### 1.2 核心原则（所有设计决策的源头）

1. **帮用户解决当前的问题。** 一切围绕"问题被解决"（问题关闭），不是"我给你写了代码"。
2. **分步授权，每一步可控。** 分析（只读）自动；写入/执行逐级授权（信任阶梯 L1-L4）。〔2026-10-05 追加裁定：**部署不是一档授权**——原写"写入/执行/部署"三档；部署类命令（`npm run deploy`/`rsync`/`docker push`/`kubectl`）按命令头判入**高危**，须逐次单独确认且**永不进信任规则**（`02` 授权后的信任机制），故不存在"部署授权"这一级——ADR-023〕；**授权后唯一可逆动是打断**。**（2026-10-05 追加裁定：本产品没有"撤销授权"这件事——批出去的动作不可追回，只能打断正在跑的轮；已写入的文件用回滚收回。"撤销"一词整体退役，不设合法含义——ADR-023）**
3. **交付可验证。** DoD 前置（动手前对齐"什么叫解决"+ 验收标准）（DoD 对齐 ⏸ V2——2026-08-15 裁决；V1 以解决确认卡（证据对账）+交付包为可验证闭环）、证据链（做了什么/怎么验）、失败可恢复（失败包/备份/回滚/半成品可带走）。
4. **不装能。** 超出数字能力 → 明说 + 给产物 + 分步指导；不静默失败、不假装搞定。
5. **上手不学。** 零学习成本：说出问题就会被解决；不学指令/不学 IDE/不注册。
6. **安静可信。** 不打扰、不炫技；过程可见但不说术语；本地优先、数据出域显式。

**原则 → 设计映射表**

| 原则       | 落地设计（§对应）                                                                                                                            | 反例（违规即缺陷）                                                                                                                |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| 1 解决问题 | 问题台账/交付包（§3.3）、DoD 前置验收（⏸ V2——不得占 V1 承诺落点）、**北极星＝问题关闭率**（唯一定义处 `08 §3.4`，本行只引用）                | 交付"我写了代码"而非"问题已解决可验证"；交付≠关闭                                                                                 |
| 2 分步授权 | 信任阶梯（§4.2）、写入模型（§3.5 接受=暂存/写入=原子 apply）、**打断** ＋ **回滚**（写前快照 `.nf-bak`）                                     | 未授权写盘／未授权高危执行（含部署类命令）；授权疲劳（步步弹窗）；**反悔无处可去**（由打断＋回滚承接，不存在"撤销授权"——ADR-023） |
| 3 可验证   | DoD 对齐（§4.1——DoD 对齐 ⏸ V2——2026-08-15 裁决；V1 以解决确认卡（证据对账）+交付包为可验证闭环）、证据链（diff/日志/前后对照）、失败包（§5） | 只报"已完成"无证据；失败不说明影响/下一步                                                                                         |
| 4 不装能   | 边界承诺（§1.3）、外部世界协调（§4.4：等待清单+触发条件+指导）                                                                               | 假装搞定域名/备案/线下；硬做做不了的事                                                                                            |
| 5 上手不学 | 场景卡片（§3.2）、非技术视图（§3.8）、人话交付                                                                                               | 首次强制教程；核心依赖快捷键/术语                                                                                                 |
| 6 安静可信 | 非模态提示条、数据出域清单（§10）、本地优先                                                                                                  | 弹窗打扰；隐式上传；面向用户抛技术术语                                                                                            |

**原则间冲突裁决**：

| 冲突                                                       | 裁决                                                                                                                                        |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 「2 分步授权」vs「5 上手不学」（非技术想一键 vs 每步确认） | 信任阶梯 + 非技术视图主路径「接受并写入」（改动说明先行，可一键）；高风险操作（删/部署）永远单独确认（＝高危档，不另设"部署授权"——ADR-023） |
| 「3 可验证」vs「6 安静」（证据 vs 不打扰）                 | 证据折叠在交付包内（人话摘要 + 详情展开），非模态                                                                                           |

### 1.3 能力边界与首次使用

**能力边界（不装能）**：

- 数字工具能力内：直接解决（文件整理/数据加工/建网站源码/修系统/做小工具/0-1 交付）
- 超出数字能力（域名/备案/线下/法律）：交付数字产物 + 分步指导——明说"我做到哪、你必须做哪"

**首次使用前提**：需要 DeepSeek 兼容 API Key（模型为 DeepSeek V4 系列；接入方：DeepSeek 官方 / Command Code / OpenCode Zen / OpenCode Go——ADR-010）。首次打开：

- 本地已有有效 Key：自动检测，直接进入启动页
- 没有：简洁配置页（选接入方 → 粘贴 Key → 验证 → 进入）
- 网络不通：提示 + [跳过（离线不可用）]

零学习成本指不学 IDE 操作，不是零依赖。

### 1.4 用户

**V1 唯一用户＝不会写代码的人**（定义处＝`08 §3.2`）；开发者面 ⏸ **V2**（2026-10-05 裁定——原「两类用户、一套内核、双视图」不再是 V1 承诺，一切验收口径须由 V1 用户给出）：

- **不会写代码的人（V1 主）** — 说出问题 → 被解决：交付数字产物（文件/源码/小工具）+ 人话说明 + 指导。看「非技术视图」（产物/预览/验收清单），不暴露术语。
- **会写代码的开发者（⏸ V2）** — 授权闭环：异常修复（定位→方案→修复→测试→部署→复核→反馈）/ 0-1 交付（软件工程模型/敏捷）。可展开技术细节、可手动编辑（编辑器=可选能力）。

### 3.5 Diff 审核

**默认审核模式（修复审计 M5）：**

用户点待审核任务或搭档改完后：

1. **先展示改动摘要**：哪些文件、几处改动、每处简述
2. 底部按钮：主按钮「全部接受并写入」、次按钮「逐处审查」
3. 用户点逐处审查 → 进入逐处模式（同原规格）

**写入时机（修复审计 M3）：**

- 逐处点 ✓ 接受 = 暂存（标记为已确认，不写文件）
- 点「全部接受并写入」或逐处审完点「写入文件」= 一次性原子 apply
- 状态栏显示「待审核: N」→ 接受后「已暂存: N」→ 写入后清零

**全部接受确认（修复审计 M1）：**

不用弹窗。diff 视图中出现确认提示条：

```
┌──────────────────────────────────────────────┐
│  确认写入全部 4 处改动？                        │
│  [写入] [取消]                                 │
└──────────────────────────────────────────────┘
```

提示条在编辑器底部，不遮挡，不模态。

**完成状态：**

```
✅ 改动已写入文件。
```

无 🎉，无庆祝动画。

### 3.6 任务列表

**多任务模型（修复审计 C5）：**

V1 采用**串行执行队列**：

- 可创建多个任务。同时仅一个在执行（分析/修改）

## 四、交互模式

### 4.1 问题闭环流（v2 重定义）

```
说出问题（对话入口，零学习成本）
  → 分析（只读自动 · L1）→ DoD 对齐（"什么叫解决"+ 验收标准，用用户的话）（DoD 对齐 ⏸ V2——2026-08-15 裁决；V1 以解决确认卡（证据对账）+交付包为可验证闭环）
  → 方案确认（方案卡——文件清单+假设+验证计划，批准/修改/重出）→ 执行（L3 分步授权）
  → 交付包（产物 + 做了什么 + 验收对照 + 下一步/复跑入口）
  → 用户确认问题关闭（交付 ≠ 解决，以关闭为终态；解决确认=声明+证据对账——证据不足不弹卡）
  → 超出数字能力部分：产物 + 分步指导（不装能）
```

**确认卡（结构化确认——2026-08-07 无阶段定论；2026-08-16 触发权升级）**：需要用户决定的点（目标确认/方案确认/解决确认/工具授权）→ 对话内嵌**确认/拒绝卡片**——卡弹出 = **会话进入 PENDING（等用户决策）**——用户不决策则模型任何动作都无效（做了白做）——用户「是」→ 推进 /「否（带原因）」→ 调整。**触发权在系统**（决策点=状态×提议×动作属性的确定性派生——模型只能提议不能制造卡；方案卡=可审阅 PlanProposal，解决卡=证据对账）——对齐竞品：Claude Code/Gemini Plan 门、Cline Plan/Act。

- 每一步可**停止**／**回滚**（失败包 + 写前快照 `.nf-bak` + 半成品可带走）〔**2026-10-05 措辞随修·两笔**：①原写"可暂停"——没有"原地续跑"语义，停手＝打断、继续＝重新开口（ADR-023／`00 §3.7.5⑤`）；②原写"撤销/回滚"——**两词同物**（唯一机制＝按文件回滚，`04:310/:323`、实现 `revertToolCall`/`.nf-toolcall__revert`，代码中不存在第二条 undo 通路）。**"撤销"一词整体退役（ADR-023 追加裁定）**——不存在"撤销授权"（批准后只能打断），收回已写入的文件叫**回滚**〕
- 开发者场景（异常修复／部署／手动编辑）＝**⏸ V2**（2026-10-05 裁定降位）。**0-1 交付留在 V1**——它是普通用户诉求（"我想要一个东西"），但验收走人话路径（§4.3／`08` P1-1）；部署类命令按高危逐次单独确认（备份→热更新→复核→反馈是**动作序列**，不是一级授权档——2026-10-05 溶解"部署授权"措辞，ADR-023）

### 4.5 对话回合礼仪（谁在什么时候开口）

> 2026-10-04 新落节（ADR-018）。本节只定**用户可观测契约**——即"用户看得见什么、看得见意味着什么"。轮次归属的领域建模（Turn 实体、身份 doctrine、驱动权拓扑）**下放阶段 C**；`00-domain-authority §3.2` 作为不变量 1 唯一措辞源的地位不因本节改变（ADR-015 #8 继续有效）。
>
> 立节约束（ADR-016 规则 1）：本节引入的**开口权 / 系统轮披露条 / 排队中徽标**均为**呈现与对话语义概念**，其权威域＝产品呈现层，不落领域状态字段——故不逐条出域归属卡；一旦阶段 C 要把它们做成 `ConversationState` 成员，须回到 ADR-016 补卡。

**C1 发言真实性**——用户气泡只能由用户的真实发言产生。搭档与系统**不得为驱动自身而伪造用户发言**（按钮回声不是发言）。推论：用户决策一经卡片落定，**下一句由搭档开口**；搭档确需向模型转述该决策时，走"搭档侧的自述/系统轮"（C4），不走用户气泡。

**C2 意图变更须显式**（射程＝**确认卡族**目标/方案/解决）——改变意图/换目标是**第二条决策通道**（延续 ADR-006），但**不得由措辞匹配推断**。产品呈现要求：活卡存续期间，卡上必须有显式出口（"改说新方向"级动作），用户经它产生的答复是结构化决策记录；用户在同一期间**直接打字**发送的文本按补充信息处理。产品承诺：**用户打的字不会被静默解释成"拒绝"。**

> **授权面不在本条射程（终审批补·2026-10-04）**：窗内**恰一**可决记录时的打字批准是 **ADR-017 裁定 3 的既有入口**（单卡/记住/批量/文本恰一＋规则命中，经 `approvalDecided` 收敛；`00 §3.2 要点 2` 同源）。二者不冲突的理由是**方向不对称**：C2 防的是"措辞匹配把用户的字**读成拒绝**"，而授权面文本匹配**只做 allow、永不触发 deny**（拒绝仍只经卡按钮带原因），且"恰一可决"门槛消除了选错对象的歧义。本条不收回该入口；若将来要收回，须另出 ADR 取代 ADR-017 裁定 3，不得靠 C2 的措辞顺带覆盖。

> 与领域权威的分歧：`intent-confirmation-domain-design.md:215` 现授权 C2 词表分流承担此通道。本契约不废"打字可换目标"（ADR-006 完整保留），只要求该通道**显式化**；`isConfirmIntent` 词表作为决策入口的资格由本契约收回。

> **提示词侧同源（对标批补）**：`src/renderer/sysPrompt.ts` 规则 ⑳ 早已逐字规定「**确认只能通过界面确认卡按钮完成**：用户文本回复永远不构成结构化确认——严禁要求用户『输入特定文字/暗号』来确认」。C2 是对 ⑳ 的产品化接管，不是新方向；**实现不得反过来依赖词表去兑现 ⑳**（词表的存在本身就是 ⑳ 被绕过的证据）。

**C2a 澄清作答 ≠ 决策**（对抗审计批补·堵 C2 打死锁）——**澄清提问**（`ask_user` 候选，含 `pending='system_clarify'` 强制澄清卡）属**对话素材采集**，不是决策点：用户打字作答与点选候选**等价有效**（sysPrompt ⑬「输入框是主通道，点选与打字等价」在本条射程内**保留**），作答即收口该提问；但点选所发的回声仍非用户发言（C1）。C2 只适用于**确认卡族**（目标/方案/解决）。

> 若不补本条：C2 字面覆盖一切"活卡"，而澄清卡也是活卡 ⇒ 用户对澄清提问打字＝"补充信息、不推进任何东西" ＋ C6「卡不因时间消失」⇒ **澄清永久悬置**，与 ⑬ 正面矛盾（契约一致性轴击穿，P0）。

**C2b 补充信息有投递义务**（对抗审计批补）——活卡存续期用户打字的定性是"补充信息"，但**不得止步于"不算话"**：它按 C3 排队送达，**投递形态钉死为"出队自成一轮"**（该输入本身准入成轮，不是折进别的轮——折入＝C7「转向」的 V1.5 另态），且该轮**首个产出须可见携带**（"已收到你的补充，卡片仍等你正式决定"级回执或上下文标注）。**（2026-10-05 互审批补：原句"在下一搭档轮携带"未钉投递形态，a3/C2b 验收口径二义。）**不产 `decision.resolved`、不改卡态。**静默收下且不推进＝说了没人理**，与 C10 取证义务同族缺陷。

**C3 输入不静默消失**——用户发送即上屏，搭档忙碌时同样上屏并带"排队中"标（与 §3.6 任务队列的 `○ 排队中` 同一徽标语言），在下一个**「回合边界」**（C13 定义：现役链收口／被打断／被新指令取代）自动转发。排队区**按条可见、可撤回（取回输入框）、可编辑、可重排**；任何"入队后被后发条目顶掉且用户无感知"的实现形态判为产品缺陷（对齐 `02 §4.12` 排队衔接 + ADR-013）。

**C4 系统自发轮可解释**——系统自发的模型轮（催推进、对账引导、卡住后的显式恢复打断）必须在对话流留一条**折叠的披露条**：一行人话说明"为什么搭档又开口了"+ 可展开**原因与触发依据**（展开的是"为什么"，不倾倒逐字内部提示词）+ 无用户气泡、无 `message_sent`（通道语义仍遵 ADR-013 与 `02 §4.12` 的 silent 定义，本节只补**呈现义务**）。理由：无披露条时，用户与测试看到的都是"消息凭空出现/幽灵占位"，二者不可区分。

**C4a 系统轮不占排队面**（对抗审计批补）——silent 轮（催推进、对账引导、恢复打断）入队时**不渲染排队条目、不计入排队徽标**；其存在仅经触发时的披露条（C4）事后交代，且披露条须注明它相对用户排队条目的触发位次（早于/晚于哪条）。否则徽标显示 N 条、flush 时混入不可见系统轮，**用户数不上数**，C3 的"按条可见"当场失真。

**C5 等待必须有可见归宿**——任何"搭档正在处理"的呈现，必须对应一条真实的在飞请求；请求终结（正常收口 / 零产出 / 失败 / 被打断）时，该呈现必须收口。**"处理中"不得成为无主状态**。

**C6 决策点有生命终点**——卡不会永远活着，也不会永远能点。**本条只管确认卡族（目标/方案/解决）；授权面（ApprovalWindow）的存续与过期语义一律归 ADR-017，本条不覆盖、不改写**：

- **跨重启/重连后确认卡旧实例不可批**——用户离开再回来，面前必须是重新提出的决策点；旧实例只可读、不可决，文案用**「上一轮会话的决策 · 请重新确认」**级措辞。
- **断线期间待决不丢**——决策内容随会话存续，回来按上一条处理。
- **确认卡不因等待时间自动消失**——自动消失＝把"用户没空答"读成"用户拒了"，属误杀。授权面的 TTL 到期/expires 语义仍按 ADR-017（`expired` 是该族专属态，不是通用词）。
- **两族过期态必须不同词**：确认卡族＝"请重新确认"；授权面＝"已过期/需重批"。同词会让用户把"不可批"读成"超时被拒"。
- 取舍注明：竞品有"审批超时自动拒"的路线（Cline/Codex），确认卡族有意不采——本产品拒绝必须带 `RejectReason`（值对象见 `04 §2.3b`），自动超时给不出原因，只能落"不可批＋重出"。

**C7 用户输入有三态投递时机**——「发出去」≠「现在生效」。产品定义：**排队**（在下一个「回合边界」自动发出——见 C13 定义，V1 默认）/ **显式打断**（对话流停止按钮，DOM 真名 `.nf-chat__send--stop`；**键盘出口 V1 未实现**——§六 的 `Esc` 权威定义是"关闭当前面板 / 取消当前操作"，不含打断，本条**不引用 Esc**）/ **转向**（在下一个工具边界插入、保留已完成工作——**V1 不做**，标 V1.5，须与 §3.6 串行队列一并设计）。任何一态都不得丢弃输入（C3 是底线）。

> 勘误：ADR-013 与本节旧稿曾引用选择器 `.nf-chat__stop`——该选择器**只存在于注释**（`ConversationPanel.tsx:2561`），真实类名是 `.nf-chat__send--stop`（`:3943`）。契约引用不存在的选择器＝不可测断言，已就地改名（历史 ADR 正文不回改，引此条为准）。若要补键盘打断出口，须先在 §六 加行并落 main 键监听，**不许两头都写而不实现**。

**C8 拒绝必须带方向投递**——用户「否」不是一次静默的关闭：`RejectReason`（方向/范围/复杂度/缺信息/修改/其他）必须①交给模型调整、②在对话流可见（"已把你的原因转给搭档"级别的回执）。**拒绝无回执＝产品缺陷**（对齐 §4.1 三确认点的"带原因"承诺——原因不能只停在事件里）。

> 卡路与打字路的分工：卡上"修改方案"自带原因输入框（`02-components` 卡交互），产出 `decision.resolved`＋reason；聊天框打字按 C2 只是补充信息、经 C2b 投递。**体验不倒退**——sysPrompt ⑳ 与 C2 同脉，且 §3.8 早已证明"卡上自带说话出口"是本产品的既有模式。

**C9 打断保留残值**——被打断的回合**已完成的工作不消失**：已写入的文件、已产出的部分内容、已跑过的验证都保留并可查；打断只冻结"接下来"，不**回滚**"已经"〔2026-10-05 改词：原写"不撤销"——"撤销"已定为 revoke 专词，此处指文件〕。回滚是另一件独立的事（写前快照 `.nf-bak` 与按文件回滚见 §4.3／交付包章，**不存在"§4.9"**——旧稿悬空引用已修），不得与打断混为一谈。

**C10 一条消息有四个状态**——发送不是瞬间成功：`已输入 → 已提交 → 已消费（真正进入这一轮）→ 失败`，四态对用户可区分。本条**分两个对象各立规矩，不得混称"重发"**：

- **① 输入重发（用户的话）——禁止自动**。提交失败（请求被中止、网络变更打断）时该条消息呈**失败态**＋可重试出口；绝不自动重发用户的输入。
- **② 轮重放（搭档的一次重试）——允许，但四个硬条件同时成立**：(i) 失败气泡**原地保留**并加"已自动重试 1 次"标，**失败态不得被重试轮替换或覆盖**（现实现 `retryFailedTurn :3030-3054` 用 `base.slice(0,-1)` 原地抹掉失败气泡，属违反）；(ii) 每一层（main 网关瞬态重试 / 渲染层续跑）**各产**时间线事件 `conversation.auto_retry`（source、errorType、轮指纹）——网关层现仅 `console.log`、无 tlog 无呈现（`src/main/gateway.ts:557/:588`），属"静默"的实质来源，且它使"最多一次"名不符实（1＋网关暗数）；(iii) 重试再失败**即停手**回落手动出口，禁级联；(iv) 重试时刻的 UI 序列不得出现"错误气泡→无→处理中"的形变空洞。
- ①②之②的"有痕单次重放"折中**成立的前提是上面四条**，只写"有痕"两字不够：痕若只在 timeline（`conversation.error`）而用户不可见，C10 仍被架空。
- 冲突登记：`tests/interaction/retry.interaction.ts:188-202` 现断言"计划确认后 service 自动续跑一次"——**不违反本条**（那是轮重放），但落地批必须按 (i)(ii) 复核其可观测性，并把"失败气泡被替换"这一现有形态列为待修。
- 本条同时是**取证义务**：nudge 死信、迟到文本没送到、请求被外部网络变更打断，都属 C10 未兑现。

**C11 搭档忘事必须可见**——上下文压缩/截断发生时，对话流须有轻量标注（"较早的对话已压缩为摘要"级别），且压缩**不得静默移除活卡的决策内容**。理由：忘事不可见时，用户会把"搭档忘了"误读成"搭档不听话"，进而给出虚假的负反馈（与 §3.9 上下文控制衔接）。

> 现状是**断链不是空头**：真压缩在 main（`src/main/compact.ts:58`、`ipc.ts:393-399 'compaction:compact'`），而渲染层唯一的压缩呈现 `.nf-compact`（`ConversationPanel.tsx:3070-3074`）读的是 `getDemoBridge().compactHistory`——**demo 假通道**，真压缩发生时对话流零呈现；`timeline.ts` 无压缩事件。落地链三小步：注册事件 `context.compacted` → `compaction:compact` 成功回推渲染层 → 复用既有 `.nf-compact` 渲染位（`styles.css:3090-3094` 已在）。

**C12 输入必须落到确定的任务**——§3.6 串行队列下，用户输入**始终归属当前活动会话**；未来放开并发（V2 多 Agent/Worktree）时，"这条消息发往哪个任务"必须先有显式选择机制才允许并发。**不得出现"消息发出去了，但进不到我正在看的那个任务"**。

**C12a 待决策期仍是"当前会话"**（对抗审计批补·堵 §3.6 与 ADR-013 的缝）——任务 A 卡在确认点等待时，A **不算 busy**（ADR-013 明载 decision-pending 不计 busy）但 A 仍是**活动会话**：此时打字归 A，按 C2/C2a/C2b 处理（确认卡族＝补充信息；澄清提问＝有效作答）。**排队中的任务（`○`）永不接收输入**；切换任务只经任务列表显式点选——**打字不构成切换意图**（与 C2"不得由措辞推断"同脉）。

**C13 单一推进点（回合级串行）**（2026-10-04 用户裁定落条款，ADR-019 D2b 的产品层落点）——一个会话**同时只有一条搭档推进链**，下一轮的发起权**只在回合边界由单点裁决**（现役链收口 / 被打断 / **被新指令取代**之后——第三项 2026-10-04 补：F7 裁定 D 的取代式准入也发生在边界上；旧定义漏它，`00 §3.7` 因此不得不自造同义词，属产品缺口）。与 §3.6「V1 串行执行队列——同时仅一个任务在执行」同构，本条把它从任务层下推到**回合层**。用户可观测推论：① 不存在两条推进链同时写同一段对话（幽灵占位、半截流、旧轮 chunk 覆盖新轮均属违反 C5/C10）；② 排队输入在**确定的那个边界**发出，次序可预期；③ 搭档自己再开口（C4 自发轮）与用户输入走**同一个仲裁点**，不是两套引擎互相抢占。**抢占本身合法**（用户新决策、显式打断都可作废在飞轮），但作废必须**同步生效**——被作废的链不得再写会话状态、不得再产生呈现。

> 现状判为对 C13 的**实现偏离**（不是新方向被遗漏）：`ConversationPanel.tsx` 内 26 个调用点各自 `++sid` 开轮、旧轮靠 500ms 轮询自杀、且在过期窗内继续写状态——判据与批次划分见 ADR-019 D1／D2a／D3。
>
> **V1 范围钉死（用户裁定 2026-10-04：先一条链完整解决用户提出的问题）**：准入形态 V1 **只有「排队」**（C7 默认态）；「折入现役回合」＝ C7「转向」，V1.5；「派生为有身份的子执行」与跨回合序列并发＝ **V2**（与 §3.6 并发解锁一并设计）。竞品的多回合并发证据（Codex `max_concurrent_threads_per_session`、Agent Teams、`/multitask` 等）**只用来定"约束的单位是回合序列"，不得当作 V1 并发的依据**。

**C13a 拒绝必须留痕**——「不受理」在 V1 对用户输入**不存在**：任何用户发送至少落为排队（C3 底线）。作废/丢弃只对**已失效的内部投递**（过期决策点答复、失效回声、被取代的自发轮触发）合法，且必须走既有可见出口——`conversation.stale_input_discarded`（ADR-015）＋重提示，**不得静默丢弃、不得回喂**。据此本产品**不采** Codex 的 "declines the input without recording or enqueueing it" 语义（那是对 agent↔agent 提交面，不是对用户输入的礼仪面）。

## 十一、版本范围

**V1 包含：**

- 首次配置页（API Key）
- 启动页（场景卡片——整理文件/做小工具/修系统/0-1 交付）
- 主工作区（问题台账 + 对话区 + 产物区交付包）
- 问题闭环流（DoD 对齐（DoD 对齐 ⏸ V2——2026-08-15 裁决；V1 以解决确认卡（证据对账）+交付包为可验证闭环） → 执行 → 交付包验收 → 确认关闭）
- 交付包（产物 + 验收对照逐项打勾 + 复跑入口 + 不装能指导）
- 问题台账（7 态状态机 / 断点续做（V1 限制：消息+台账恢复、状态机不跨重启——V2 会话快照，2026-08-15 裁决） / 复开）
- 0-1 交付流（无阶段确认驱动——目标确认 → 方案批准（PlanProposal）→ 解决确认（证据对账）——无固定阶段；分步确认/迭代可 demo）
- 数字产物交付（文件整理/合并/转换/清洗 + 变更预览 + L3 授权）
- 信任阶梯（L1-L4 渐进授权 + 快照回滚 + 委托规则）
- @文件引用 + 搭档须知（.neonforge）
- 设置（语言 / 默认视图 / 提醒开关）+ 内置插件注册（无市场）
- 深色主题（仅深色）

**V1 明确不做：**

- Inline 代码补全
- 多 Agent 并行（Worktree 隔离）
- 专用部署通道／部署工具（部署以 **bash 高危命令**承载，逐次单独确认、永不进持久规则——"部署"不是一种授权档，ADR-023）
- 插件市场
- Git GUI
- 社交/协作
- 闲聊/画图
- Web 版
- 浅色主题
- 多语言（只做中文和 English）
