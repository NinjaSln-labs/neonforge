**V1 = DeepSeek-only（指模型，非接入方）。** 产品档位 `flash` | `pro`；上游名由各接入方 `/models` 列表过滤 DeepSeek 后挑选（默认 flash → v4.1；官方 alias `deepseek-flash`）；接入方经 `src/main/providers/` 注册表切换（ADR-010：DeepSeek 官方 / Command Code / OpenCode Zen / OpenCode Go；旧配置默认 Command Code）；模型行为调优挂 ModelProfile（`toDeepSeekParams` 等），不挂 provider。

## 3. 确认点规格化（目标驱动核心）

### 3.1 三个状态确认点

| 确认点                                                                                                                                               | 含义                               | 确认动作（结构化）                       | 未确认时模型活动边界                                                                                                                                                                                                                                   |
| ---------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- | ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **GoalConfirmed**                                                                                                                                    | 用户确认「做什么」——目标驱动的原点 | 确认目标 / 重新描述（带原因）            | 只澄清（不产生执行动作）                                                                                                                                                                                                                               |
| **PlanConfirmed**（原 ExecutionConfirmed——2026-08-16 语义澄清：用户确认的是**方案**（PlanProposal），「执行」是确认后的自动结果）                    | 用户确认「怎么做」                 | 批准方案 / 修改 / 重出（带原因）         | 只给方案（不 write/edit/**有副作用 bash**——2026-08-14 澄清：探索性只读命令如 ls/cat 放行，其判定与授权 preApproval 同源 classifyReadonly——2026-08-16 第 14 轮审计 #1 更名，原 classifyAction；只读例外与 §3.5b ActionGate 只读自动同源——02/04 同口径） |
| **ResolutionConfirmed**（原 AchievementConfirmed——2026-08-16 语义澄清：「达成」是模型声明（CompletionClaim），用户确认的是「问题解决」（证据对账）） | 用户确认「问题解决了」             | 已解决（证据对账通过）/ 还要改（带原因） | 持续执行（不收敛）——模型必须继续产出/验证                                                                                                                                                                                                              |

> 2026-08-16 更名说明：执行确认→方案确认、达成确认→解决确认——用户在整个流程中确认的对象始终是「提议」（目标提议/方案提议/完成声明），不是「状态」；「执行」「达成」是确认后的自动结果。详见 §3.6 触发权与 `intent-confirmation-domain-design.md`。

### 3.1b 确认语义（行业共识）

- 确认 = **结构化显式动作**（确认卡按钮）——非确认词匹配（误触发不可靠）
- 确认点未处理（未确认未拒绝）= **等待**（blocking——模型停在该确认点——不推进、不默认放行）
- 确认/拒绝显式三态（对齐 OpenHands USER_CONFIRMED/USER_REJECTED、Cline allow/always/reject）

### 3.2 单一 PENDING 状态机（会话级——等用户决策——领域核心）

**任何需要用户决策的点（卡弹出）→ 会话进入【PENDING——等用户决策】——pending 是会话级（Conversation 聚合承载——2026-08-07 领域定论），Task（会话内执行单元）不承载 pending。授权面事实不直接住槽：需批准的执行请求以**授权窗口（ApprovalWindow——`ConversationState.approvalWindow`，请求记录集合）**为真相源，`pending='approval'` 是窗的单向派生呈现（ADR-017，原"工具级授权等待是会话级 pending 的一部分"据此精化）**：

```
任何需要用户决策的点（卡弹出）──→ 【PENDING——等用户决策】
    ├─ 目标确认卡（大阶段）
    ├─ 方案确认卡（大阶段——PlanProposal 批准）
    ├─ 解决确认卡（大阶段——完成声明+证据对账）
    ├─ 授权卡（小阶段——工具级**与 plan-batch 合并授权卡**——窗内 pending 请求的呈现；不批准则后续无法继续，影响大阶段）
    └─ 强制澄清卡（`system_clarify`——**委派呈现**：占槽，但答复经 ADR-015 #3 递归透传给底层真实决策点，本身不是独立求决项；打字作答与点选等价——产品 C2a）
                                        │
               pending 下模型动作全部无效（做了等于白做——不执行不生效）
                                        │
                            ┌───────────┴───────────┐
                         用户「是」              用户「否」
                            │                       │
                    状态推进 + 模型继续       状态回退 + 模型调整
```

**要点**：

1. **槽只有一个**——所有确认点/授权卡统一「等用户决策」状态（来源只是卡类型与授权窗口，不各自建 pending）。授权面为**单窗、N 可寻址目标**（不变量 7 改述——ADR-017）：窗是 `requests: ApprovalRecord[]` 集合，每请求一条可寻址记录；窗存续不增槽
2. **pending 下模型动作无效**——模型后续工具调用不执行（做了白做）——状态保持 pending——**存在活 pending 时，用户决策是下一个状态的唯一输入**：确认卡族（goal/plan/resolution）针对当前决策点实例（instanceId+kind 匹配）寻址；授权面针对窗内记录以 **requestId** 寻址（main 签发、跨进程跨重启唯一；`approvalDecided` 为四入口＋规则命中的单一收敛函数，allow 与 deny 同权入态），**且此唯一性含其预先规则裁决**——session/persistent 规则命中＝`decidedBy:'rule'` 的同门登记，是先前用户决策的延迟执行、非新增输入源。实例/请求不符＝不作数（no-op＋stale 事件，ADR-015·ADR-017）。无活决策点（pending＝none 且窗无可决记录）＝无可推进实例（清理/任务边界路径，ADR-015 #3 门前置）。**锚名注**：本节条目编号为「要点 N」；跨文旧引用写作「§3.2 规则 2」者与「要点 2」同指一条（v4.x 改词未同步引用面），一律以本节编号为准
3. **授权卡同属 pending**——授权面是小阶段（工具级），但不批准则后续无法继续——影响大阶段——与确认卡同一状态机；授权决策一律**写窗内记录**（不只是清槽），窗内 pending 可决记录的呈现即授权卡
4. **决策点触发权在系统，不在模型文本**（2026-08-16 增补——三视角调研结论：竞品无一按模型标记触发确认；学术「介入点按动作属性」）：模型只能产出**提议**（结构化值对象：GoalProposal/PlanProposal/CompletionClaim），**卡（决策点）出现 = 状态 × 提议 × 动作属性的确定性派生**（§3.6）——模型措辞不直接弹卡；**授权面派生链细化（ADR-017）**：动作属性 ask → main 于 needApproval 裁决分支签发记录入窗（queued/pending）→ 槽位置再经窗态 × 槽空闲派生（要点 5）——"是否需批"的裁决权始终在 main 规则引擎（§2 判定表、02 §4.8）
5. **槽呈现互斥（ADR-017）**：**窗含 pending 请求 且 无确认卡占槽 ⇒ `pending='approval'`（单向派生）**；确认卡接管期间窗存续——不置槽、不推号（`decisionInstanceSeq` 为 goal/plan/resolution 族专用，授权面无实例号）。**让回方向不在本条措辞**：槽释放后何时把 queued 记录升回 pending，唯一措辞处＝**§3.8.6 通道让回触发**（v1.2 曾在句尾自带"且无 Running 轮"谓词，与 §3.7.2 出口③、`02 §4.12` 各写一份互斥条件＝三源病灶，2026-10-05 互审收口）。窗 pending+queued 归零 ⇒ `windowResolved`（槽释放）。D5 hasApproval effect 退役（UI 现象不再代理 pending）。**本要点的族优先级由 §3.8 I-FOCUS-2 承载、触发条件由 §3.8.6 承载——此处只留置槽方向的派生式，不再作独立措辞源（ADR-022）。**
6. **与轮次轴的分工（2026-10-04·§3.7 落位；同日 P0 修正收窄；互审批再收窄）**：本节**要点 1–4（含不变量 1 的唯一措辞源地位）**不被 §3.7／§3.8 改写或并列另立——「槽只有一个」说的是等待（谁在等谁），**不得**被读成「轮只有一个」；反之 §3.7「至多一个非终态轮」管推进，也不得被读成等待轴。**例外一处（已就地写明）**：要点 5 属**呈现派生条款**，其**让回方向的触发条件**改由 §3.8.6 承载（本节不再持有任何触发谓词）——这是 §3.7／§3.8 对本节唯一的合法改动，其余一律只引用。

### 3.3 确认点 = 推进门槛（不变式）

- 未确认目标 → 不进入执行（模型只澄清）
- 未确认方案 → 不产生执行动作（write/edit/bash——结构性：状态机未到下一态）
- 未确认解决 → 不收敛（推进保障保持——不能自宣布完成停手）

### 3.4 PENDING 下模型动作无效（做了等于白做——审计 Major 1 修正）

**pending 状态（等用户决策——此处 pending 指槽被置位，含窗派生的 `'approval'`）下——所有工具都不放行**：模型后续任何动作（read/search/write/edit/bash/check-capability…）一律**无效——不执行不生效**（做了白做——状态保持 pending——唯一措辞源见 §3.2 规则 2）。**无害 ≠ 有用**：read 等只读动作虽无副作用但**没用**（用户决策未到——结果无意义——同样白做）——pending 下模型不做任何事（停住等用户）。**确认卡占槽、窗内含未决记录（queued）时窗不释放槽、不改变本段效力——冻结判据恒为槽，不为窗**（窗是待决内容的真相源，冻结仍由 §3.2 单一 PENDING 承载——ADR-017）。

**用户决策后放行**：

- 用户「是」→ **确认卡族**：状态推进 → 模型**根据决策重新做**（不是恢复 pending 前的动作——决策改变状态，动作跟随状态重新生成）。**授权面**：决策写入窗内记录（approved＋decidedBy/decidedAt）；执行由调用层凭窗内记录**二次 execute 携 requestId**（main 校验 id ∈ 执行日志 journal ∧ phase 允许 ∧ argsFingerprint 等值——批 A 行 B 拒）；执行结果经 `approvalExecutionSettled` 收敛回写（批了但失败＝failed，防双真相）；槽由窗派生释放（ADR-017）
- 用户「否」→ **确认卡族**：状态回退 → 模型调整后再来。**授权面**：决策写入窗内记录（denied，原因必填——§3.6 RejectReason）＋reason 回填模型＋拒绝记录进 actionGate 同轮同类短封（机制防绕过，语义不变）
- **恢复/重连＝journal 对账（ADR-017 v3.3）**：窗快照与 main 执行日志按 requestId 对账三判——未决∧≤approved→**存续可决**（用户被中断的决定不丢）；done→对账收敛 settled('done')；started∧¬done→**uncertain**（执行效果不可证＝升格用户裁决，resolveUncertain 唯一出口、禁自动重放）；无行可判（旧档退化）→未决 expired、approved∧未 settled→settled('failed')

### 3.5 门控优先级（PENDING vs 计划清单——审计 Major 2 修正）

```
PENDING（方案未确认）──→ 所有动作无效（不管文件在不在清单——等「方案确认」卡）
    │（用户批准方案）
    ▼
方案已批准 ─→ 按计划清单判定：
    ├─ file ∈ 清单 → 放行执行
    └─ file ∉ 清单 → 拒绝 + 拒绝带边界（「X 不在批准清单（批准的是：A/B/C）」）
```

**优先级规则**：pending（方案未确认）是**状态机冻结**（先——所有动作无效）；计划清单是**文件级**边界（后——用户批准方案后逐文件核对）。pending 时不进入清单判定。

### 3.5b 动作属性门控（ActionGate——2026-08-16 新增，与会话冻结正交）

**门控 = 会话状态冻结（§3.2/3.4） × 动作属性分级（本节）两个正交维度**（对齐 DSH sandbox×approval 正交、Codex is_safe_command、Deep Code scope 表）：

```
ActionGate(action, policy) → { verdict: allow | ask | deny, attribute, risk }
  属性判定（classifyReadonly——与模型自评无关）：
  - readonly（read/search/LSP/check-capability；bash 命令头白名单+链递归+git 子命令级）→ allow（只读自动）
  - network-read（curl GET localhost 等无写副作用）→ allow；外网 GET → ask（安全）
  - in-plan（write/edit 且文件 ∈ plannedFiles）→ allow（清单内自动——§5）
  - out-of-plan / hazardous（写清单外/危险命令）→ ask 或 deny（策略配置——deny 为机制拦截）
```

**ActionAttribute 值对象**（门控判定输出类型——kind 权威枚举，与模型自评无关；2026-08-16 第 12 轮审计 #2 补——原 §3.5b 用而未定义）：

```
ActionAttribute {
  kind: 'readonly' | 'in-plan' | 'out-of-plan' | 'network-read' | 'hazardous'
  basis: 'tool-type' | 'command-head' | 'command-chain' | 'git-subcommand' | 'plan-list'
  // basis = 判定依据（审计追溯：为什么判成这个 kind）
}
```

**部署不是一种动作属性（2026-10-05 用户裁定，ADR-023）**：`npm run deploy`／`rsync`／`docker push`／`kubectl` 等由 `classifyReadonly` 的**命令头判定**归入 `hazardous`（ask 或 deny——策略配置），**永不进 session/persistent 信任**（`02` 授权后的信任机制：bash 无 path 一律不进入信任）。⇒ 产品旧写「写入/执行/**部署**逐级授权」「部署授权（L4）」是**能力空头且与上述不变式正面冲突**（它暗示存在一档可记住的"部署授权"），已随修——工具面无部署工具，ActionAttribute 五类亦无部署类，不存在第三条通路。

**优先级**：会话冻结（pending）优先于 ActionGate（§3.5 不变）——pending 时任何动作无效，不进入属性判定；ActionGate 的 deny 为机制拦截（`tool.blocked` 事件[^gate-denied-rename]），ask 才产生授权请求（ApprovalRequest：toolName+subject+reason+risk——2026-08-16 第 13 轮审计 #8 补 toolName 字段，对齐 04 §2.3b；请求记录由 main 签发经 approvalRequested **入授权窗口**——呈现与闸在窗，ADR-017）。

[^gate-denied-rename]: 历史文稿曾写 `gate.denied`；注册表与实现事件名为 `tool.blocked`。

### 3.6 决策点触发权（2026-08-16 新增——三视角调研结论：竞品 9/9 无一按模型标记触发确认；学术共识「介入点按动作属性分层，不按模型自评标签」）

**模型只能「提议」，不能「制造决策点」**：

```
模型产出提议（结构化值对象——非文本标记）：
  GoalProposal{ statement, assumptions }          // 目标提议（含关键假设）
  PlanProposal{ summary, files[{path,reason}], assumptions[], verificationPlan[] }  // 方案提议
  CompletionClaim{ summary, evidence }            // 完成声明（含证据——§4.2）
  ── 提议本身不产生任何状态变化，只进入「待求值」──
系统派生决策点（确定性纯函数 deriveDecisionPoint(state, proposals, pendingActions)）：
  - 目标提议存在 && !GoalConfirmed      → 决策点：goal（目标确认卡）
  - GoalConfirmed && PlanProposal 存在 && !PlanConfirmed → 决策点：plan（方案卡）
  - Goal+Plan 已确认 && 动作属性需授权  → 决策点：approval（main 签发记录入窗——授权卡＝窗内 pending 记录的呈现，槽位由窗派生，ADR-017）
  - CompletionClaim 存在（证据完备）&& !ResolutionConfirmed → 决策点：resolution（解决确认卡）
```

**关键性质**：

1. **决策点 = 状态 × 提议 × 动作属性的确定性函数**——同一输入永远同一决策点；模型措辞不参与判定（原 pendingCardToShow 以模型文本为输入的建模废除）
2. **提议是值对象**（结构化内容：假设/证据/验证计划）——不是文本标记；解析层（parsePlanProposal/parseCompletionClaim）负责从模型输出结构化，判定层只消费结构
3. **决策内容快照**（decisionContent——呈现与审计的唯一来源）：卡弹出时携带完整提议内容，确认/拒绝事件记录快照（「用户确认了什么」可追溯——2026-08-15 run4 实证的追溯缺口）
4. **用户主动确认通道保留**（goalFallback 语义重定义）：用户可在无提议时主动发起确认（对齐竞品 Plan 门——用户发起 vs 模型触发）——但卡出现的**默认路径**是确定性派生

| ⑤   | **「暂停」不建本体**（2026-10-05 用户裁定，ADR-016 规则 4＝错位走溶解）：轮次轴只有**继续**与**停止（打断）**，没有第三种"被按住的原轮"。三处落点——用户侧说"暂停"＝出口④显式打断；系统侧"自动暂停"（同签名连续 ≥3）＝**无推进的终态化**（`Settled{Failed｜Empty}`）＋停手告知（**走 C4 披露条，不是搭档气泡**）；"回复继续就接着做"＝一条普通 `user-input` TurnInput **成新一轮**（§3.4·C1 同脉）。⇒ **No-Hold 句：终态或被作废的轮不得被"恢复"，恢复永远是新轮**（I-T2／I-T10 的推论，写明以禁实现造 `resumeTurn` 语义）。任务轴的"审核时队列暂停"**不在溶解范围**——归 N2 TaskQueue |
| ⑥   | **「撤销」整体退役**（ADR-023）：**收回单次批准不存在**——批出去的动作不可追回，只能打断正在跑的轮；**收回已写入的文件＝回滚**（唯一机制 `.nf-bak` 按文件，代码中不存在第二条 undo 通路）。产品 §1.2 原则 2／§1.3 表行／§4.1／§4.5 C9 四处措辞随修。**注意与本票 ⑦ 的分工**：原 L4「可降级撤销」里的"撤销"指的是**收回已记住的规则**——那**不是空词而是缺设计**（缺口 **G12 权限域**，提案＝`docs/design/permission-domain-model-proposal-2026-10-05.md`；§3.9 为其落位预留号，**尚未存在**），故该措辞的去处是权限域，不得读成"用户不需要控制记住的授权"                              |
| ⑦   | **「部署」不是一种动作属性，也不是授权档**（ADR-023 Decision 6）：`npm run deploy`／`rsync`／`docker push`／`kubectl` 等按 `classifyReadonly` 的**命令头判定**归入 `hazardous`——**高危是兜底档，不是与写/读并列的第四级**；产品旧写「写入/执行/部署逐级授权」与「部署授权（L4）」已随修，并消掉一处与 `02`「bash/高危永不进入 persistent」的正面冲突。**它的正解位置＝权限域的策略表条目（G12 提案 §4 候选轴系），不是轮次轴，也不是信任阶梯的一档**                                                                                                                                 |

> **与 §3.2 的辨析（禁止互吞）**：**「槽只有一个」（§3.2 要点 1）说的是 PENDING 槽——管"谁在等谁"；本节「至多一个非终态轮」（I-T1）说的是驱动资格——管"谁在推进"。** 二者独立成立、互不派生：可以有槽空而一轮在跑（正常执行），也可以有槽被占而无轮在跑（decision-pending，不计 busy）。任何一侧新增措辞都不得改写另一侧，不变量 1 的唯一措辞源地位不因本节改变（ADR-015 #8 继续有效）。

### 3.8 发问通道与焦点律（2026-10-04 新增，ADR-022·缺口 G10）

> 射程：**同一时刻"谁在向用户发问"**。§3.2 规格化等待的语义（槽），§3.7 规格化推进的语义（轮），本节把「槽只有一个」从呈现条款升为正面规则，并钉死**焦点是派生量**。律文正文在此，设计取证与三型否决记录见 `docs/design/waiting-item-two-axes-proposal-2026-10-04.md`（v2）与 ADR-022——**本节不复述 §3.2/§3.7**，只建立引用与取代关系。

**3.8.1 判据：通道独占，不是"等谁的动作"**

一个会话同一时刻只有**一条**向用户发问的通道（＝§3.2 的槽）。占通道的是**求决项**：决策卡族（goal／plan／resolution）＋ 授权记录；**澄清卡是底层求决项的委派呈现**（占槽、不另立第二项）。其余"等待"不占通道，各自按既有次序规则走：

| 等待事实                                            | 占通道                                                                                                                     | 次序／存续规则（**沿用既有，不新建律**）                                                                                                                                                                                |
| --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 确认卡族（goal/plan/resolution）                    | **是**（唯一）                                                                                                             | ADR-015 实例寻址；C6 不因时间消失、跨重启旧实例不可批                                                                                                                                                                   |
| 授权记录（窗内 N 条）                               | **是**（让位于确认卡族）                                                                                                   | ADR-017 单窗 N 可寻址／`requestId`／存续可决／恢复三判                                                                                                                                                                  |
| 澄清族 `system_clarify`                             | **是——委派呈现**（互审批改判；旧稿写"否"与 ADR-015 #3／`conversationState.ts:118` 的 `pending='system_clarify'` 正面相反） | **不另立求决项**：答复经 ADR-015 #3 递归透传给底层真实决策点，`front` 仍只有一个（＝底层那件），故 I-FOCUS-1 不被违；C2a 打字与点选等价有效。**三型否决的起因据此重述**：否决理由是"它不是第二个求决项"，不是"它不占槽" |
| 待准入输入 `QueuedInput`                            | **否**                                                                                                                     | I-T13／I-T14 准入全序与 FIFO；C3 按条可见                                                                                                                                                                               |

| **处级待审核 diff（产品 `§3.3`「待审核: N 处」）**  | **否**（N 条并存）                                                                                                         | **H4 两处分裁**：属 N1 `ChangeReview` 独立聚合，不是"等用户的一个动作"                                                                                                                                                  |
| 任务级 `◉ 待审核`                                   | 经**解决确认卡**占通道                                                                                                     | **H4**：它是 resolution 的队列呈现，走第 1 行规则，不另立体系                                                                                                                                                           |
| Problem `awaiting-input`／"一键继续"（产品 `§4.4`） | **否**（互审批裁）                                                                                                         | 台账是**跨会话记录**（`02 §4.13`——状态机不跨重启），不占当前会话通道；"一键继续"的领域身份＝一条 `source='user-input'` 的 TurnInput 经准入点成轮，与用户打字同门，不另开第二条通道                                      |

**3.8.2 两轴分离（决定面存储，焦点面派生）**

```
决定面（权威存储；字段面沿用 §3.4／ADR-017，本节不新建轴）
  未决 undecided（＝可决） | 已决 resolved{approved|denied} | 已结算 settled{done|failed}
  | 失效 expired（仅授权面 TTL——ADR-017；确认卡族无自动超时，C6） | 不可证 uncertain（升格为新的求决项，禁自动重放）

焦点面（派生，不存储）
  front  正在向用户发问（可被寻址、显眼）
  back   尚未轮到（仍存续、仍可见、仍可经显式入口答复）
```

**3.8.6 通道让回触发（`drainQueued` 的唯一措辞处——互审批新增，ADR-022 补漏）**

```
槽被释放 ∧ 无 Running 轮（I-T1／I-T5）⇒ 取窗内**入态序最高**的未决记录升回 pending（置槽、卡重弹）
```

- **为什么必须带"无 Running 轮"**：让回的语义效果是把用户重新拉回求决面；若此刻有轮在跑，卡重弹会立即冻结该轮全部动作（§3.2 要点 2／§3.4）＝**假推进**，正是 I-T17 要防的形态。
- **为什么不得写成"无活决策点"**：要点 2 定义「无活决策点＝`pending='none'` 且窗无可决记录」，而 queued 记录**即可决**（§3.8.2"未决即可决"）——该谓词在"还有待升记录"时永不自真＝**死锁，卡永不重弹**。旧稿 §3.7.2 出口③写的正是它，与要点 5 的"且无 Running 轮"构成同迁移两读法（一死锁一假推进），本批解开。
- **它是派生重算，不是权威写入**（I-FOCUS-3）：存档里的 `queued` 值只是投影快照，读到即重算；跨重启后无 Running 轮 ⇒ 触发自然成立 ⇒ 卡重弹（授权面存续可决——ADR-017 恢复三判；确认卡族走"请重新确认"态——C6／a7，两族语义相反见投影契约）。

### 4.1 推进的判定（与 StuckDetector 同源——2026-08-16 同步）

**（2026-10-04 词查收口：本值对象粒度＝Round，改名令见 §3.7.5——`TurnProgress` → `RoundProgress`，其中 `hasPlannedFiles`／`remainingCount` 属 Task 级另置；下文字段语义不变。）** `TurnProgress` 扩展：**有副作用工具成功 / 新 read / 结构化提议输出 / 完成声明带证据** 均算推进。「只说不做」判定从「无工具调用」改为「无推进」（防模型输出提议被判停滞→escalate 打断合法链——坑 99 教训）。

### 4.2 完成证据（2026-08-16 新增——学术共识：self-verification 不可靠，完成判定必须对账外部证据）

**完成 = 声明 + 证据 + 用户对账**：

```
CompletionClaim{ summary, evidence: CompletionEvidence }
CompletionEvidence{ verification: [{command, output?, passed?}], diffs: [{path}], pendingQuestions: [] }
```

- **无证据不对账**（不变量，ADR-011）：verification 空 / passed=false / 零条可代跑或可代跑条 V1a 失败 → 声明不完整 → **不进入 resolution 决策点**（「已解决」卡不弹）→ 回填「缺验证」引导模型补证据；unverifiable 仅标注；**pendingQuestions 不阻塞**（ADR-008）
- 用户确认的是「声明 + 证据」的对账结果（用户原始目标 vs 模型声称完成），不是对声明的背书
- 证据不足诊断事件：`completion.evidence_missing`

## 5. 宿主强制边界（模型漂移防护——行业共识）

- **方案提议（PlanProposal——2026-08-16 新增值对象）**：模型方案确认前的结构化提议——`{ summary, files: [{path, reason}], assumptions[], verificationPlan[] }`——**文件清单含理由、方案含假设清单与验证计划**（用户确认的是「看到全部假设并接受」——竞品计划工件/学术「确认内容含未验证假设」）；渲染为可审阅方案卡（批准/修改/重出）
- **计划清单（PlannedFiles）**：由已确认的 PlanProposal.files 派生（单一来源——不变量 6）——approve-files（2026-08-08 坑 95 改名，原 plan_approval）追加语义保持——模型只能写清单内——**清单对模型显式可见**（系统提示注入）
- **追加语义**：分批 approve-files 合并（Codex rules AppendRule 同理——不覆盖前批）
- **拒绝回填边界**：写清单外被拒 → 拒绝信息带清单内容（「X 不在批准清单（批准的是：A/B/C）」）——模型回到边界内
- **拒绝带原因（RejectReason——2026-08-16 新增值对象）**：用户拒绝决策携带结构化原因 `{ kind: direction|scope|complexity|missing-info|modify|other, text?, target? }`——`modify`=「修改」决策（拒绝+修正内容→模型重提议，不单列状态分支）；回填模型调整方向（对齐 Cline denial reason / Deep Code「不要绕过」——防模型无方向重试）

## 6. 能力与环境（Capability BC）

- **环境是事实来源**（一次检测：runtime/依赖/工具链/宿主 runtime）——**能力是语义视图**（从环境推导——不独立二次检测——消除双源）
- **Ledger 回填**：执行结果回填能力状态（bash 失败归因 → 降级 failed；成功恢复）——自学习
- **环境快照注入模型**（项目根/runtime/依赖/能力——模型开箱即知——不需要探索确认环境）

## 9. 术语表（无阶段）

| 术语                             | 定义                                                                                                                                                                                                                                                                                                                                                                     |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 目标驱动（Goal-driven）          | 任务围绕「达成什么」组织——目标确认是推进的原点                                                                                                                                                                                                                                                                                                                           |
| 确认点（Confirmation Point）     | 推进的门槛——目标/方案/解决三处用户确认（2026-08-16 更名：执行→方案、达成→解决——§3.1）                                                                                                                                                                                                                                                                                    |
| 推进（Progression）              | 跨确认点的状态转换——唯一通道是用户确认                                                                                                                                                                                                                                                                                                                                   |
| 自推进（Self-progression）       | 确认点内部的模型自主工作（工具链）                                                                                                                                                                                                                                                                                                                                       |
| 推进保障（Progress Guarantee）   | 确认后防只说不做的推进决策（强制对象=推进≠调工具——§4）                                                                                                                                                                                                                                                                                                                   |
| 计划清单（Planned Files）        | approve-files 批准的可写文件集合（宿主边界）                                                                                                                                                                                                                                                                                                                             |
| 能力视图（Capability View）      | 从环境推导的能力状态（ready/missing/failed）                                                                                                                                                                                                                                                                                                                             |
| 环境快照（Environment Snapshot） | 一次检测的事实（runtime/依赖/工具链）——注入模型                                                                                                                                                                                                                                                                                                                          |
| 会话时间线（Session Timeline）   | 单会话所有步骤统一日志（可观测性）                                                                                                                                                                                                                                                                                                                                       |
| 问题台账（Problem Ledger）       | 跨会话问题记录（goal/decisions/authorized/pending 快照）——断点续做/复跑（Conversation BC 子域——2026-08-15 补建模）                                                                                                                                                                                                                                                       |
| 确认卡（Confirm Card）           | 确认点的结构化 UI（确认/拒绝按钮）                                                                                                                                                                                                                                                                                                                                       |
| 提议（Proposal）                 | 模型产出的结构化主张（GoalProposal/PlanProposal/CompletionClaim）——不产生状态变化，只进入待求值（§3.6）                                                                                                                                                                                                                                                                  |
| 决策点（Decision Point）         | 需要用户输入才能继续的确定性状态——状态×提议×动作属性的纯函数派生（§3.6）                                                                                                                                                                                                                                                                                                 |
| 决策（Decision）                 | 用户对决策点的响应：确认 / 拒绝（带原因）/ 修改（拒绝+修正内容）（§3.6）                                                                                                                                                                                                                                                                                                 |
| 证据（Evidence）                 | 完成声明的可核验支撑（verification 命令输出/diff 对账/遗留问题）——无证据不对账（§4.2）                                                                                                                                                                                                                                                                                   |
| 方案提议（PlanProposal）         | 文件清单+假设+验证计划——plannedFiles 单一来源（§5）                                                                                                                                                                                                                                                                                                                      |
| 完成声明（Completion Claim）     | 模型「做完了」的主张——必须附证据（§4.2）                                                                                                                                                                                                                                                                                                                                 |
| 拒绝原因（RejectReason）         | 拒绝决策的结构化原因（kind/text/target）——回填模型调整（§5）                                                                                                                                                                                                                                                                                                             |
| 动作属性（Action Attribute）     | 工具调用的客观性质（只读/网络只读/清单内/越界/高危）——ActionGate 判定（§3.5b）                                                                                                                                                                                                                                                                                           |
| 授权（Approval）                 | 对「动作属性判定为需询问」的调用，main 签发**授权请求记录**（requestId 跨进程跨重启唯一、不透明）入会话级**授权窗口（ApprovalWindow）**并向用户呈现（ApprovalRequest：toolName+subject+reason+risk），用户允许（一次/会话/永久三档）或拒绝（带原因）；四入口＋规则命中经 `approvalDecided` 收敛（ADR-017——2026-08-16 第 15 轮审计 #2 补 toolName；设计 §2 通用语言同源） |
