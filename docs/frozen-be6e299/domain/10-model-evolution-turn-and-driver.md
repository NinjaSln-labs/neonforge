## 1. 基线：现行模型已经给了什么

现行领域模型（`docs/domain/00–09`，ADR-001～017 累积）在**"等什么"**上有完整本体：

| 已有本体                       | 载体                                                                              | 强度                                            |
| ------------------------------ | --------------------------------------------------------------------------------- | ----------------------------------------------- |
| 会话级单一 PENDING（状态机）   | `00 §3.2`（不变量 1 **唯一措辞源**）＋`04 §1.2` Conversation 聚合成员 `pending`   | 有身份（`decisionInstanceSeq`）、有转换、有事件 |
| 决策点实例寻址                 | ADR-015（双概念：槽 kind × 实例 seq；单一身份门；`restorePending`）               | 可机验                                          |
| 授权窗口（ApprovalWindow）     | ADR-017（`requestId` 不透明身份＋main journal 三判＋规则三档）                    | 跨进程跨重启可证                                |
| 推进的**判定**（不算推进什么） | `00 §4/§4.1`（ProgressGuarantee 档位表；TurnProgress 值对象；StuckDetector 同源） | 有 VO、有服务                                   |
| 完成证据对账                   | `00 §4.2`（CompletionClaim/CompletionEvidence；无证据不对账）                     | 不变量级                                        |
| 问题台账跨会话生命周期         | `02 §4.13`／`04 §1.5` Problem 聚合＋快照                                          | 有聚合                                          |

**一句话诊断**：**「等人」有本体，「谁在推进」没有本体。** 现行模型能精确回答"这张卡是哪一次呈现、这条批准是哪一条记录"，却回答不了"这条正在改会话状态的产出属于哪一次开口、它还有没有资格改"。

### 3C F7——**已裁＝选项 D**（本节保留三解对照作历史存档，勿当现行）

「待授权期用户发**新指令**」的**轮次归属**：现行文本只说"可直接处理"（`02 §4.12`＋ADR-013 裁定 2），**从未裁定它落在哪个轮**；而 `00 §3.2 要点 5`（窗含 pending 记录⇒槽仍为 approval）＋要点 2（pending 下模型动作一律无效）使"直接处理"若直接成新轮＝**假推进**。三解（A 有痕解算→释放槽→原轮 Superseded→新轮准入／B 同轮续跑不释放槽，但用户不点卡就永久冻结＝C2a 死锁族复发／C 冻结粒度收窄到单条记录——须改不变量 1 射程，不属合作负责人可自裁范围）与代价见提案 §10 末。**〔2026-10-05 对齐〕终裁＝D（焦点轴换人：`pending→queued`、决定轴一字不写值、释放槽、原轮 Superseded、准入新轮；卡的重弹归 `00 §3.8.6` 触发）——A 的"有痕解算"措辞已在 ADR-021 附件 2 就地划去；D 的追问掉出缺口 G10（§3D），已落 `00 §3.8`＋ADR-022。**

### 3D 缺口 G10（**已闭合**——落 `00 §3.8`＋ADR-022）：等待项的**焦点轴**与**优先律**未本体化（v3 新增，比 N1/N2 更基础）

> **〔2026-10-05 编号勘误·必读〕** 本节代码块里的 `I-FOCUS-1/2/3` 是**v1 律稿编号**（1 焦点唯一／2 优先／3 换焦必可见），与已落位的 `00 §3.8.3`（1 通道独占／2 次序律／3 **焦点派生化**／4 换焦不改决定）**同 token 不同指**。现行权威只认 `00 §3.8`；本节仅作设计过程存档，照此编号引用于任何地方都是错引。另：本节的 `WaitingItem` 超类型与"求决／待进／待启"三型分类**已被否决**（`00 §3.8.5`）。

**起因**：F7 裁定过程中发现——`queued/pending` 看着像决定的两个阶段，其实**一根轴都算不上完整**。三条事实：

1. `conversationState.ts:88`：**`DecidableApprovalState = {queued, pending}`**——可决性**不区分**这两级。既然决定语义相同，二者之差必在另一根轴上。
2. `conversationState.ts:443`＋`:422/474/494`：`drainQueued(windowResolved(…))` 在**每次窗转换后重算** queued↔pending ⇒ 它是**派生态**，却被**物化存进权威记录**（＝单源化要消灭的形态：一旦存了，就多出"谁忘了重算"这一族故障）。
3. `00 §3.2 要点 5` 已裁「**冻结判据恒为槽，不为窗**」——槽才是焦点；记录存的 pending 只是焦点的副本。

**正解是两根正交轴**：**决定轴**（未决／已批／已拒／已结算／过期／不确定）× **焦点轴**（现在轮到被问／还没轮到／已被问过）。

**普适检验：我们领域里所有"等待项"都是同一形，却各造词汇**

| 等待项                 | 决定轴                                   | 焦点轴                   | 现行表达                 | 毛病                                             |
| ---------------------- | ---------------------------------------- | ------------------------ | ------------------------ | ------------------------------------------------ |
| 授权记录（ADR-017）    | approved/denied/failed/expired/uncertain | queued ↔ pending         | **同一枚举混放**         | 两轴压一轴，且派生值被物化                       |
| 决策点实例（ADR-015）  | resolved（带原因）／未决                 | 活动／过期不可批（C6）   | `pending` 槽 + `expired` | "过期"是时效（决定轴）、"不可批"是焦点轴，混着说 |
| 输入队列（本进化新造） | 无——被**消费**而非被决定                 | Queued ↔ Admitted        | `QueuedInput`            | 只有焦点轴，恰好证明该轴可独立存在               |
| 任务队列（§3.6）       | 完成／取消                               | 排队 ○／待审核 ◉／执行 ● | 三态                     | 三轴混一根，且对象序缺失（＝N2）                 |
| Turn（本进化新造）     | 六个终态（Settled 五子态＋Voided）       | Running／**Suspended**   | `Suspended`              | 命名干净——只做焦点轴                             |

**G10 的形状（v1 提案形，存档；终形＝最小形，超类型与三型分类否决）**：

```
WaitingItem {
  undecidedness  决定轴：undecided | resolved{...} | settled{...} | expired | uncertain   ← 权威存储
  focus          焦点轴：front | back                                                    ← 派生，不存储
  归属           turnId / taskId / requestId（谁在等、等哪件事）
}
deriveFocus(state) → (唯一焦点项, 其余项的排队序)     // 纯函数，可 L1 断言
I-FOCUS-1 焦点唯一律：同时至多一个 front 项
I-FOCUS-2 优先律（现只隐含在实现里，必须显式）：确认卡族 vs 授权记录 vs 系统 nudge 的先后 ＋ 同类 FIFO ＋ 唯用户显式重排可改序且留痕（I-T14 是其一半）
I-FOCUS-3 换焦必可见：发事件留痕 ＋ 对话流可感（C3 按条可见／C13a 有痕）——本进化 I-T18 是它的一个实例
```

**〔2026-10-05 互审新增缺口 G11 → **已裁＝溶解，不建本体（ADR-023，用户裁定原文见该 ADR Context）**〕**——用户裁定原文：「用户按得不是暂停，其实是继续和停止。不存在暂停这个状态，只有继续或者停止。如果确实要做暂停，我们需要考虑这个暂停到底属于谁——是用户暂停还是系统暂停。」裁定形状：轮次轴上**只有继续与停止**，"暂停"是"停止"的误名 ⇒ 走 ADR-016 规则 4 的**溶解**（不建第三态、不建许可位、不加第三根面）；落点＝`00 §3.7.5⑤`（词汇收口）＋`00 §4` 停手行＋产品两处措辞随修。**残留问题搬家不丢弃**：①"停手后系统不该自己再开口"（nudge／escalate 的抑制窗口）属 **G7**——**外部一致证据：凡有暂停处必建 fence**（OpenHands `_explicit_interrupt_generation`、Cline "FENCE FIRST" 置栅栏再 abort、Codex `clear_pending` 防在飞批准被读成拒绝），不解决则**用户刚按下的停止会被自家催推进顶掉**（G7 必裁子项，非理论风险）；②任务队列的"审核时暂停"属 **N2**；③停手告知走披露条而非搭档气泡属 **C1/C4 礼仪随修**。**原缺口描述（存档，勿再当票追）**：产品 `00-product-design §4.1` 写「每一步可暂停/撤销/回滚」，`§4.5 C7` 只有排队／打断／转向三态，**没有"暂停"的领域对应物**；若做成"轮停在 Round 边界不发起下一次往返"，则它既非 Running（无在飞请求）又非 Suspended（不等用户决策），**I-T5 `busy ≡ ∃ Turn ∈ {Running}` 当场把它判成不忙**，呈现与排队投递都无依据。未裁问题＝①暂停是焦点轴还是推进轴上的态？②暂停期用户输入算排队还是算新指令？③暂停与 §3.8 通道的关系（暂停时新卡能否弹）？⇒ 独立票，不进本批。

**代价与影响面（诚实列出）**：①去物化会改 ADR-017 已 landed 的 `queued/pending` 语义——是**精化**（"它是焦点副本，不是决定阶段"）而非推翻，`DecidableApprovalState` 不变，故恢复三判与 journal 不受损；②优先律一旦显式化，就要回答"新弹的授权卡能否抢占当前焦点"与"确认卡族谁在前"，这与 C6（卡不自动消失）×C4a（系统轮不占排队面）三处都相关；③`§3.6` 三态需重述为两轴（N2 TaskQueue 一并解决）；④持久化层存档里的 queued 值需要一次迁移解释（读到即重算，不作权威）。

**判定：本批补的是真缺（G1–G3 全部有产品承诺悬空作证据），但"补全"不成立——G4–G8 是真漏，其中 G5 是我自己写不变量时当场暴露的（不变量挂在未定义词上）。**

## 7. 结论
