# 证据卡：NeonForge 长会话内存与事件循环基线（2026-11-23）

> 本卡是**产品级性能基线**，不是 SLO 达成声明，也不是人类可用性研究。
> 对象是真实 Electron 产品（主进程 + preload + 渲染器），在隔离用户数据、假 Key 与本地 mock SSE 上游下连续运行 120 分钟。
> 渲染器会话由脚本每分钟发送一轮，非真人交互；覆盖 30/60/120 分钟采样。

## 测量方法

- 加载真实 `dist/main/main.js`，隔离 `userData`/`HOME`/`XDG`；把三个产品 provider 固定 origin 在探针进程内路由到本地 mock（不改产品代码/注册表）。
- 启动页填入首句 → 点「从零开始」→ 产品自身的 `initialPrompt` 自动发送 第 1 轮；之后每分钟在真实 composer 里填入第 N 轮并点发送。
- 每轮等待产品自身 `done` chunk（渲染器侧独立监听），最多 60 s；连续 3 轮失败才中止。每分钟采样（计划 120 个采样点；本轮有效样本 WSL 113 / Mac 119）：
  - `app.getAppMetrics()` 各进程 working set；Linux `/proc/<pid>/smaps_rollup` PSS（macOS 无 PSS）；
  - 主进程 RSS / heap；渲染器 `performance.memory` heap；
  - 渲染器 DOM 中 user/assistant 消息数、assistant 正文总字符数、`localStorage` 体积；
  - 主进程与渲染器事件循环延迟（1 s tick 的偏差）。
- 产品自带的对话压缩（`history.length > 100` 时压缩为摘要 + 保留最近 20 条）与 `SESSION_MAX = 50` 的持久化上限均被真实触发，是本轮要观察的行为。

- 所有 111（WSL）/ 117（Mac）轮均收到 `done`，轮次与 `done` 计数完全一致，无失败。
- 消息数在 60/120 分钟出现回落（WSL 第 55 轮时可见 14/15 条，第 111 轮时 30/31 条），对应产品压缩触发（100 条历史 → 摘要 + 最近 20 条）；`localStorage` 体积最多到 184 KB 后进入平台。
- WSL 的 PSS 在第 1 分钟为 319 MB（启动/首轮抖动），10 分钟后回落到 179–297 MB（平均约 217 MB）；120 分钟为 218 MB。10–90 分钟拟合斜率约 **+0.50 MB/分钟**，90–120 分钟为 **−0.25 MB/分钟**，即总量进入平台而非线性增长；增量主要来自渲染器 Tab PSS（10–90 分钟 +0.57 MB/分钟、90–120 分钟 +0.33 MB/分钟），Browser 主进程 PSS 反而小幅下降。

- Mac 无 PSS，working set 含共享页；不能把 571 MB 当作唯一内存。WSL 的 PSS 才是同口径唯一驻留近似。

## 结果：事件循环延迟

| 平台 |        主进程 p95 最大值 |      主进程单次最大 |   渲染器 p95 最大值 |      渲染器单次最大 |
| ---- | -----------------------: | ------------------: | ------------------: | ------------------: |
| WSL  | 27 ms（第 49 分，45 轮） |  217 ms（第 12 分） | 13.9 ms（第 80 分） | 72.4 ms（第 80 分） |
| Mac  |                     3 ms | 278 ms（第 118 分） |  9.2 ms（第 35 分） | 13.1 ms（第 51 分） |

- 常规 p95 在主进程 1–4 ms、渲染器 0.1–9 ms 量级；单次尖峰出现在压缩/渲染大消息或系统调度，不是持续劣化。
- 120 分钟内未观察到随轮次增长的延迟趋势；Mac 的 p95 上限 3 ms 说明其调度更平滑，单次 278 ms 尖峰出现在第 118 分（对应压缩后的长消息重渲染）。

## 解释

- **WSL（唯一有 PSS 的平台）**在 120 分钟内总 PSS 处于 179–319 MB（10 分钟后平均约 217 MB），主进程 RSS 63–86 MB（峰值 224 MB 仅在首分钟）、渲染器 heap 18–21 MB；分段斜率显示 90 分钟后进入平台，没有随轮次线性增长。这支持「长会话在 mock 短消息场景下不会无界增长」的初步结论。
- **Mac 工作集从 383 MB 升到 571 MB（+188 MB）**，其中 Tab +99 MB、Browser +79 MB、GPU +11 MB。10–90 分钟线性拟合约 **+1.41 MB/分钟**，90–120 分钟降到 **+0.14 MB/分钟**，同样进入平台。由于 macOS 无 PSS，这部分可能是共享页重复计入、也可能是真实增长；需要 `footprint`/`vmmap` 复核后才能判断唯一驻留。
- 主进程 RSS 与 Browser working set 同步上升（Mac），而 WSL PSS 中 Browser 反而从 134 MB 降到 45 MB（启动缓存释放），说明两平台的计费与缓存策略不同，不能横向比较绝对值。
- 产品压缩在约 50 轮（100 条消息）触发一次；`SESSION_MAX = 50` 让 localStorage 在 184 KB 附近封顶。两者共同解释了 60/120 分钟的可见消息回落。
- 事件循环延迟没有随轮次恶化；单次 217/278 ms 尖峰需要结合当时是否正在压缩来解读（本轮未逐事件对齐）。

## 限制

- **mock 上游**：固定短回复、无工具调用、无文件上下文、无 reasoning；真实会话的 token 量、工具结果与 reasoning 会显著更大。
- **脚本非人类**：每分钟固定发送一轮，不代表真人节奏、阅读时间或中断/恢复。
- **单一机型/平台**：WSL2+xvfb 与一台 2018 MacBook Pro；无 Windows、其他 macOS 或 Apple Silicon。
- **macOS 无 PSS**：Mac 数字是 working set（含共享页），不能与 WSL PSS 直接比较。
- **压缩与持久化行为**：只观察了 100 条阈值与 50 条持久化上限；未覆盖手动清除、跨重启恢复或多会话切换。
- **测量开销**：每分钟一次 `app.getAppMetrics()` + 一次渲染器采样，开销很小但并非零。
- **不是 SLO 达成**：没有提案阈值对应「长会话」，本轮只建立基线。

## 安全与边界

- 仅假 Key 与隔离用户数据；真实凭据环境变量在启动前剔除；原始 JSONL 只落 `.scratch/`（gitignored）。
- 会话内容为固定生成的探针文本，不含用户文件、路径或真实对话。
- macOS 运行通过 SSH 启动，凭据不涉及；运行结束后进程已退出。
