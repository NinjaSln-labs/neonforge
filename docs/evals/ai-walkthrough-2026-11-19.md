# NeonForge AI 辅助可用性走查报告（2026-11-19）

> 性质：**AI 辅助启发式走查 + 脚本化 UI 任务断言**。不是人类用户研究，不是 SUS/HEART 基线，不产生 SUS 分数，也不代表目标用户意见。
> 证据：`apps/desktop/tests/interaction/aiWalkthrough.interaction.ts`（手动运行，不进入常规 CI）；截图目录 `.scratch/evals/ai-walkthrough-2026-11-19/`（不入库）。
> 关联：`sus-heart-study-kit-2026-11-19.md`、`governance-gap-assessment-2026-11-18.md`、`ai-risk-register-2026-11-19.md`（R-07）。

## 1. 走查边界

- 环境：Linux/WSL2 + Vite dev renderer + Playwright Chromium，不是打包后的 Electron 安装包。
- 模型与工具：`MockBridge` 提供固定模型脚本与工具结果；**没有真实模型、Provider、网络或工具副作用**。
- 真实部分：渲染器状态机、目标/方案确认卡、计划清单门、授权卡、拒绝路径、交付包验收与问题台账均为产品实现。
- 信任模式：走查使用 `strict`，以便稳定呈现写入授权卡；默认 `standard` 下，已确认方案内的根内写入可能按 ADR-015 自动执行，两者不能混读。
- 截图只保存在 `.scratch`，不入库；本报告不含真实用户数据，也不含 SUS 分数、任务完成时间或 HEART 指标。

## 2. 方法

1. 用 Playwright 驱动 3 个脚本化场景，覆盖研究套件中的 5 个任务：首次配置、目标确认、方案确认、写入授权/拒绝、交付包验收。
2. 共 10 个自动断言、8 张全页截图；断言只验证可观察 UI 状态，不评价模型能力。
3. 对截图做 AI 启发式评审，检查维度包括：系统状态可见、用户控制与自由、一致性与标准、错误预防、识别而非回忆、帮助与说明。
4. 结论分两类：**自动断言结果**（客观、可复现）与**启发式发现**（AI 判断，未经用户验证）。

复现：

```bash
cd apps/desktop
NF_AI_WALKTHROUGH=1 npx playwright test --project=interaction tests/interaction/aiWalkthrough.interaction.ts
```

脚本耗时不含 Playwright webServer 启动时间，且**不是人类任务完成时间**。

## 4. 正向观察

- 首次配置页目标清楚，明确说明 Key 只存本机；没有把 Key 写入仓库或日志。
- 目标卡与方案卡使用结构化按钮（确认目标 / 重新描述；确认执行 / 修改方案），没有依赖自由文本确认词。
- 授权卡显示工具、路径、写入内容预览、后果说明（「会先备份原文件，之后可一键还原」）与「拒绝」路径；拒绝后明确显示「已拒绝授权——未执行」。
- 计划清单门在计划外写入时给出可操作提示，而不是静默执行或只报通用错误。
- 交付包的「确认问题关闭」在验收项未勾选时禁用，并提示先完成验收（`DeliveryPanel.tsx:569-588`）。

## 5. 启发式发现（AI 判断，未经用户验证）

严重度：P1 阻断任务；P2 影响理解、信任或一致性；P3 打磨项。本次未发现 P1。

### F-01（P2）确认动作生成新的「问题」台账条目

- 证据：截图 03、04、04c 左侧「问题」列表。一个任务在确认目标/方案后出现三个条目：「做一个待办应用」「确认，目标清楚了」「确认，按方案执行」。
- 机制：确认按钮发送用户文本（`ConversationPanel.tsx:870-876`），而每条用户消息都会创建问题实例（`MainWorkspace.tsx:636-658`）。
- 影响：问题列表被确认词污染；断点续做/复开时可能选错上下文；用户可能误以为开始了新任务。
- 建议：把结构化确认（目标/方案/授权结果）记录为当前问题的领域事件，而不是新问题；同任务内按活动问题去重。

### F-02（P2）「允许执行」与「允许并记住」的语义重叠

- 证据：截图 04、04b、04c 的授权卡；点击「允许执行」后，信任条显示「本次任务已记住：app.ts」。
- 机制：`approveToolCall` 对 write/edit 也会调用 `addTrust`（`useToolApproval.ts:121-129`）；`rememberAndApprove` 再次调用 `addTrust`（`useToolApproval.ts:215-223`）。两个按钮在文件写入场景下产生相同的任务级文件信任。
- 影响：用户无法形成正确的授权范围心智模型；「允许并记住」看起来权限更大，但实际效果与「允许执行」相同，容易加剧审批困惑与疲劳（风险登记册 R-07）。
- 建议：文件写入只保留一个批准按钮并明示范围（「本任务内此文件自动」或「仅本次」）；若保留两个按钮，需让行为真正不同并在卡上解释清楚。

### F-03（P2）首次配置无法显式选择模型

- 证据：截图 01 只有「接入方」与「API Key」；模型 ID 输入仅在 Provider 返回 `needs-model-id` 时出现（`ConfigPage.tsx:174-192`）。
- 影响：任务「首次配置 Provider/模型」只完成一半；使用内置模型列表的 Provider 时，用户不知道实际会调用哪个模型，后续在设置页看到不同模型时容易困惑。
- 建议：首次配置显示「默认模型：X」并提供更改入口；若 Provider 有多个模型，直接给出选择；若只有一个默认模型，也至少明示名称。

### F-04（P3）内部工具名与后端错误文本直接出现在用户界面

- 证据：截图 02-04 的 `propose_goal`、`propose_plan`、`write` 原始工具名；授权卡中的「需要授权（L3）——approved=true 后执行」。
- 影响：开发者术语进入主要任务路径，增加理解成本；同一事件同时出现工具芯片、状态句与友好提示，信息重复。
- 建议：面向用户的卡使用本地化动作名；原始工具名/错误码放入「查看详情」；合并重复状态文案。

### F-05（P3）拒绝后仍显示多重「处理中」

- 证据：截图 04c（点击拒绝 500 ms 后）：气泡「搭档处理中…」、行内「搭档处理中：工具执行中…」、底部状态栏「搭档处理中」与「停止」按钮同时存在。
- 影响：用户无法判断助手是已停下等待下一步，还是仍在执行；「停止」按钮暗示仍有任务在运行。
- 建议：拒绝后立即结束当前回合并释放 working；统一为一个状态通道；若必须保留处理中状态，明确写「已拒绝，等待下一步」。
- 备注：截图是拒绝后的瞬时状态，需在真实构建中复核是否持续存在。

### F-06（P3）「已解决」先于用户验收出现

- 证据：截图 05：验收项未勾选时顶部状态已是「已解决」；勾选并关闭后才变为「已关闭」。
- 影响：用户可能把模型自报的「已解决」误读为已通过验收。
- 建议：在用户完成验收前使用「待验收」；「已关闭」只用于用户确认关闭后的状态；文案与状态机保持一致。
