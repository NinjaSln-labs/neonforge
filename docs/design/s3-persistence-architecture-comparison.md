# S3 持久化架构对比：纯事件重放 vs 聚合快照＋账本并存

> 目的：计划 §8 移交必答项 2「聚合快照 vs 事件重放的取舍」的段5 决策材料（用户裁「先出对比再定」）。
> 事实均来自本会话现场读码（HEAD `c6e024e`）＋段3 frozen §5/§6/§7，非记忆。日期 2026-10-07。

## 0. 共同前提（两方案都满足）

- 契约 A1：7 仓储面**方法名集合不变**（`repos/index.ts:9-75`）。
- 契约 A3／段3 §6：聚合写入与 `TimelineRepo.append` **同库同事务**；append 失败⇒整事务回滚。
- 契约 B3：恢复＝账本重放；重复恢复＝no-op。
- 契约 A2：`save→重建实例→find` 读回**逐字段相等**（7 聚合各一条往返）。

## 1. 现场事实（决定两方案可行性）

| 事实 | 值 | 出处 |
|---|---|---|
| 聚合有序列化面吗 | **无**（无 `toJSON`/`fromJSON`/`snapshot`） | 全仓 grep 零命中 |
| 聚合构造器 | **private**＋static 工厂（`Delegation.create`／`DecisionPoint.raise`／`Turn.start`／`InstructionQueue` ctor） | 各聚合文件 |
| 事件载荷能否重建聚合态 | **大部分能**：`DelegationReopened.reopenCount`、`TurnEnded.terminal`、`DecisionResolved.resolution`、`InstructionQueued.{itemId,delegationId,origin}`、`ScopeAmended` 版本对——载荷键即重建输入 | `timeline.ts:78-200` |
| **不可重放字段** | `Turn._expiredWrites`（I-13 过期令牌写入计数器）**不在任何事件**（段3 §5 尾注：聚合状态字段、不入 timeline 闭集） | `Turn.ts:30,99` |
| 内存态现状 | `InMemoryTimelineRepo` 持 `TimelineLog`（append 先落账后分发）；聚合各自持 Map/字段 | `repos/memory/*` |
| S1 落盘模式 | `configStore` 式：构造注入路径、同步写、损坏容错、`0o600`、原子性弱（直接 writeFileSync） | `plannedFilesStore.ts` |
| 重启点 | `getRuntime()` 建单例；`resetRuntime()` 供测试 | `domainRuntime.ts` |

## 2. 方案甲：纯事件重放（Event Sourcing Lite）

**做法**：只持久化 **timeline 事件日志**（append-only 落盘）。聚合不是持久实体——启动时从日志重放出 7 聚合的内存实例；`save()` 退化为「更新内存缓存 / no-op」（状态权威＝日志）。

| 维度 | 评估 |
|---|---|
| 改动面 | **小**：只需 TimelineRepo 持久实现（1 个文件）＋启动重放器（1 个服务）＋ `save()` 语义调整（7 内存实现改为「缓存更新」共 7 处小改）；**零聚合序列化面** |
| 新增代码 | timeline 持久适配＋重放器（约 2 文件） |
| 确定性风险 | **高（阻断级）**：`Turn._expiredWrites` 不可重放 ⇒ 重启后 I-13 计数器归零，**违反 I-13 DoD「计数 0」的可追溯性**（重启前若已有过期写入，重放后丢失）。须为它单开事件或单列持久面——与「不入 timeline 闭集」直接冲突（段3 §5 尾注明令不得扩闭集） |
| 事务语义 | 天然满足 A3（唯一持久物就是日志，同事务＝同一次 append 落盘） |
| A2 往返 | 需**新增重放器**才能「save→重建→find」；测试要造事件流 |
| 与段3 §6 措辞 | 「账本重放（RecoverableSpec）」字面最贴 |
| 回滚成本 | 低（改动集中在 timeline 适配） |

## 3. 方案乙：聚合快照＋账本并存（Snapshot + Log）

**做法**：每个聚合持久化**自身序列化状态**（新增 `toSnapshot()`/`fromSnapshot()`），timeline 事件另存。`save()` 写聚合快照。恢复＝载入快照（＋可选用账本补差）。

| 维度 | 评估 |
|---|---|
| 改动面 | **中**：7 聚合各加 `toSnapshot`/`fromSnapshot`（私有构造器加 fromSnapshot 工厂）＋7 持久实现（或 1 个通用 JSON 仓储泛型）＋启动载入器；**新增聚合序列化面 ≈ 7×2 方法** |
| 新增代码 | 序列化 7 对方法＋持久适配（约 4-8 文件） |
| 确定性风险 | **低**：状态直接存取，`_expiredWrites` 等非事件字段**天然保留**；无重放确定性负担 |
| 事务语义 | 需显式：聚合快照写＋timeline append 落同一事务（段3 §6 例外条款）——比甲多一点协调 |
| A2 往返 | 天然（save 快照→fromSnapshot→find），直接可测 |
| 与段3 §6 措辞 | 「账本重放」需解释为「快照为主、账本为 WAL/审计」——**与 I-12 字面「恢复只还原账本（持久化态）」有张力**：若权威是快照而非账本，I-12 的「账本」措辞需澄清 |
| 回滚成本 | 中（改动分散在 7 聚合） |

## 4. 关键分歧点（裁决依据）

1. **I-13 计数器**：`Turn._expiredWrites` 不可重放且**不得入 timeline 闭集**（段3 §5 尾注）⇒ 纯重放方案（甲）**要么丢该计数器、要么扩闭集犯规**。这是甲的硬伤。
2. **I-12 字面**：「恢复只还原账本（持久化态）」——甲字面最合；乙需把「账本」解释为含快照的持久化态（可辩，但需在详设写明口径）。
3. **改动面/复杂度**：甲显著小（ponytail 倾向甲），但甲撞 I-13 硬伤。
4. **契约 A2/A3**：两方案都能满足。

## 5. 推荐（待用户裁）

**推荐方案乙（快照＋账本并存）**，理由：
- 甲撞 **I-13 不可重放**硬伤——除非为 `_expiredWrites` 单列持久面（等于给 1 个聚合开特例持久化，反倒比统一快照更扭曲）。
- 乙「低确定性风险、A2 天然可测、非事件字段天然保留」，且落 `configStore` 既有模式，7 聚合序列化面是本阶段**必要复杂度**（段3 §7「仓储只存聚合本体」已隐含聚合本体可存取）。
- I-12 字面张力可控：详设写明「账本＝含聚合快照的持久化态；事件日志为审计/重放源」，并在 S3 ADR 记此口径（F8）。

**备选**：若用户更重「最小改动＋纯事件源纯度」，选甲，但须先裁定 `_expiredWrites` 的持久去处（这一条本身就要回段3 §5／段2 改闭集＝铁律②回退，成本高）。
