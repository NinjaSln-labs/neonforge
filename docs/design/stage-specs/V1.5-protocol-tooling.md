## 附录 B：spike 结论（S0 执行后回填）

### 环境口径声明（2026-08-31——用户明确）

本附录全部 spike 数据刻画的是 **Command Code 网关路径**（`deepseek/deepseek-v4-flash`——NeonForge 当前生产通道），**不等同于 DeepSeek 官方 API 行为**（网关可能转换/丢弃请求字段——Spike-3 已实证一例）。产品定位：**模型层 DeepSeek-only，接入方不绑定**（ADR-007）——网关能力差异（thinking 参数、tool_choice 限制等）按「接入方能力矩阵」条目记录，不写成模型普适结论；接入方直连对照（`DEEPSEEK_API_KEY` 已具备）仅在评估直连 adapter 时补测。

**设计原则（用户明确）**：即便单一接入方，其能力面也随时变化（官方亦可能调整 thinking 参数/工具行为）——架构**只依赖最小公共 denominator**（tools + tool_choice:auto + 提示词 + 客户端状态机），任何 provider 特定能力一律「能力检测 + 优雅降级」，不作为硬依赖。V1.5 设计恰好符合：spike 发现的所有限制均被提示词引导/状态机方案绕开，无一需要 provider 特性支持。

### S0 收口附加结论（对 S1-S3 实现的补充影响）

5. gateway 流式重组须保留重组器捕获的 **tool_call id**（首个分片携带——串行多轮 tool 结果喂回依赖它）
6. gateway args 解析层照搬 spike-lib `parseArguments`（string→再 parse 回退）+ parse 失败保留 rawArguments 重试 1 次
7. gateway 落地时 onDelta 类回调移出半包 JSON 的 try 块（spike-lib 容错副作用教训）

### 对 S1-S3 的既定影响（spike 已锁定）

1. propose_plan path 字段描述采用 2b 硬化文案；落地解析统一走 splitPathReason 候选制 + parse 失败重试 1 次
2. 硬序门/引导触发一律提示词（明确「直接调用 XX 工具、禁止先 bash/read/search 探索」措辞——Spike-2 实证 49/50 直调）
3. gateway 流式解析增 `delta.reasoning_content` 独立通道（思考文本 currently 丢失）
4. 强制 tool_choice 不可用——任何「确保模型调 X 工具」需求走提示词 + 状态机硬序门
