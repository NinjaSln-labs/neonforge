## 1. 用户裁定原文

> 「bash，部署授权，属于 权限领域驱动模型里得，不应该，而且可以记住得部署授权，现在只有在用户允许后只是本项目内记住，只不过现在权限领域驱动模型设计得实现设计得不够，权限应该是分档，高危应该是兜底，普通文件读应该默认允许，机密文件读需要授权，改项目仓内应该默认允许，改其它目录文件需要用户授权，授权应该可记录，可编辑，应该有沙箱模式/YOLO模式等。」

拆成八条设计要求：**D1 分档**／**D2 高危＝兜底**／**D3 普通读默认允许**／**D4 机密读需授权**／**D5 仓内写默认允许**／**D6 仓外写需授权**／**D7 授权可记录、可编辑**／**D8 有沙箱模式／YOLO 模式**。

## 3. 诊断：这是轴向缺失，不是补两个 case

### 3.1 一根枚举压了三根轴

现行 `kind` 同时回答三个不同问题：_这是什么动作_（读/网络/写/执行）、_目标处于什么授权态_（在清单内/外）、_风险有多高_（hazardous）。用户要的 D1「分档」不是第四种 kind，而是把这三根轴**分开**，再加两根缺失的轴（作用域、敏感性）。

### 3.2 「沙箱」必须先拆成两件事（否则 D8 会反过来吃掉安全底线）

- **沙箱边界（scope 谓词）**＝目标在不在项目根内——现行不变式用它约束"记住"的射程（沙箱外永不进信任）。
- **沙箱模式（mode 档位）**＝门控松紧的一种运行模式。

这两句差一个"内"字，语义相反：**"沙箱内自动放行"是安全边界；"沙箱模式下自动放行"是把门控关掉**。现行文本已在同一词上走两侧（`00:420`「允许并记住（沙箱内自动）」＋产品 §4.2 L1「只读…静默」）。⇒ D8 落地前必须先把 mode 与 scope 分名，否则"模式"一上，五条不变式的字面含义当场漂移。

### 3.3 模式与信任阶梯也是两回事

`§4.2` L1–L4 说的是**能力解锁程度**（观察/建议/操作/委托），Mode 说的是**门控松紧**（同样允许写，问不问）。现有文本把"分步授权/沙箱内自动"混在阶梯行里描述。若引入 Mode 而不划开，YOLO 会被读成"L4"，而 L4 的既有语义是"重复任务设规则"——两者正交。

## 4. 候选轴系（提案形，待裁后落位）

```
判定的输入（三根正交轴＋一张规则表，全部客观可判、与模型自评无关）
  ActionClass  动作类型：read | write | execute | network        （工具与命令头判定）
  TargetScope  目标域：  repo | outside | system | confidential   （路径/命令目标判定；confidential 是正交标记）
  Mode         模式：    standard | sandbox | yolo               （用户显式选择；默认档见 F9-2）
  RuleTable    规则表：  已记住的裁决（once/session/persistent——ADR-017 三档沿用），作用域＝项目（见 F9-4）

裁决（唯一输出，纯函数）
  decide(action: ActionClass, target: TargetScope, mode: Mode, rules: RuleTable)
    → allow | ask | deny
  兜底序（D2）：deny 是**下限**——任何记住规则、任何模式都不得把已被判 deny 的抬成 allow；
              高危集合（删除/格式化/写系统路径/外网写/机密读）在 yolo 下仍至少 ask（此句强度见 F9-2）
```

对照八条要求：D3＝`(read, repo|outside, 非 confidential) → allow`；D4＝`(read, confidential) → ask`（且**永不进规则表**＝记住也不静默）；D5＝`(write, repo) → allow|ask`（强度取决于 F9-3 是否让"计划清单"退为可选优化）；D6＝`(write, outside|system) → ask`，sandbox 模式下→deny；D1/D2＝上表结构与兜底序；D7＝规则表是一等公民（可列出/可编辑/单条收回）；D8＝Mode 轴。

## 7. 与现行权威的冲突登记（参照，不是约束）

1. `ActionAttribute.kind` 五值混三轴 ⇒ 待推翻（候选轴系 §4）——`00 §3.5b`／`04 §2.3b` 同步重构。
2. `read` 不看路径即默认放行 ⇒ 与 D4 冲突（P-2）。
3. 「沙箱」单一名两义 ⇒ 违 P-5；引入 Mode 前必拆。
4. 信任阶梯行内混"分步授权/沙箱内自动" ⇒ 与 §3.3 划界冲突（`§4.2` 表需重述）。
5. 规则不可编辑／不可列 ⇒ 与 D7 冲突；`clearSessionGrants` 与 `setRules` 之间缺"列出・改・单条删"三操作。
6. `out-of-plan` 与"仓外"两义未分 ⇒ F9-3 任一解都要先分名。

## 9. F9-3 的涟漪（裁定即登记，防落位时走样）

**"清单退为可选优化"≠"清单没用了"**。清单在旧模型里同时干着两件事，降级只降掉第二件：

| 清单的旧职责                                                                  | 降级后                                                              |
| ----------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| **方案确认的内容载体**（用户确认的是文件清单＋假设＋验证计划——`00 §5`／§3.6） | **保留**，一字不动                                                  |
| **allow 的唯一来源**（`in-plan→allow`，其余弹卡/deny）                        | **撤**——allow 的来源改为作用域（repo 内）；越界写与机密读仍逐次授权 |

⇒ 连带必须重述三处：`00 §5`「模型只能写清单内——宿主强制边界（防模型漂移）」改写为**"宿主边界＝作用域白名单（repo 内）＋机密/高危下限档"**；`00 §2` 判定表「Workspace（计划清单）vs Conversation（写边界）」行的归属判定要改（写边界判定权从"读清单"移给 Policy BC 的 `decide`）；产品 `§4.2` L1–L4 与 §3.5 diff 审核文案同步。**若不写这张表，落位文本会出现"确认卡还在但清单不再决定放行"的读感断裂——那正是把柱子拆掉还自以为没动的形状。**
