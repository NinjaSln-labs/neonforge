# 为什么 NeonForge 只做 DeepSeek

> NeonForge 设计思考 · 第 3 篇（终篇，共 3 篇）· 2026-08
> **NeonForge**——为 DeepSeek 打造的 AI 问题工作台：你之所向，我之所往；你之所定，我之所行。说出你的问题，拿到结果。[GitHub](https://github.com/NinjaSln-labs/neonforge)
> 产品定位：AI 问题工作台——**不是**多模型客户端

## 先回答最常见的质疑：「只支持一个模型，是不是太小了？」

多模型客户端（ChatGPT 壳、Claude 壳、聚合网关）是 2024 年的正确答案——模型能力差异巨大，用户需要选择权。

但**agent 工作台不是壳**。壳的深度止于「把用户的话发给模型再展示回复」；工作台要的是「模型能在你的项目里可靠地干活」——这需要把应用和模型**绑在一起优化**。绑在一起的前提是只服务一个模型。

## 单模型深度集成，换来了什么

### 1. 前缀确定性（上一篇的延续）

KV 缓存命中的前提是**前缀字节级稳定**。多模型意味着每换一次模型，system prompt/工具定义/输出格式全要重调——前缀缓存被打回原形。只服务 DeepSeek，我们才能把 system 模板、工具 JSON schema、预热请求的参数（`thinking=none`、`max_tokens=1`）焊死成常量。

### 2. 成本结构可以算得清

- DeepSeek 的 API 定价让「预热请求」这种**为性能多花的钱**可忽略（`max_tokens=1`）
- 1M 上下文 + 便宜 → 「塞更多」的诱惑大，但我们用 LSP 精准注入**主动少用**——因为便宜不意味着免费，而是**可以大方地做性能优化而不心疼**
- 成本透明（任务估价/用量条/预算上限）是产品承诺，单模型让估算误差小一个数量级

### 3. 工具生态对齐一个行为模式

DeepSeek 的工具调用格式、`reasoning` 字段、角色约定——我们围绕它写了授权引擎（L1-L4 信任阶梯）、工具执行链路、推理可视化。这些在换模型时**全部要重写**。单一模型 = 把复杂度花在「把一件事做到极致」而不是「兼容 N 种行为」。

## 但深度不止于模型：工作台的核心是「确认卡」

只做单模型让我们有余力做更重要的东西——**把「动手干活」变成一条每步都有门槛的可靠链路**：

- **确认卡 = 推进门槛**：目标 / 方案 / 解决三处结构化确认（可审阅方案卡：文件清单 + 假设 + 验证计划；解决卡：证据对账）——触发权在系统，模型只能提议，不能制造卡
- **宿主强制边界**：模型只能写批准清单内的文件（approve-files 批量授权），清单外写入被拒并提示边界
- **分步授权**：写文件、执行命令逐项授权（风险明示 + 写前快照可回滚）；「允许并记住」免去重复打断；高危命令永远单独确认
- **问题 = 一等公民**：问题台账 + 会话快照 + 断点续做 + 复跑——批准的文件清单跨重启保留

这些机制的价值密度，取决于「只服务一个模型」换来的专注。

## 商业逻辑：DeepSeek 生态是现在最大的「价值洼地」

- 中文开发者/非技术用户群体庞大，但**深度适配 DeepSeek 的桌面 agent 工具稀缺**——多数人用通用客户端，前缀缓存、预热、LSP 精准注入这些优化没人替他们做
- 我们把「便宜模型 + 极致优化」做成组合拳：预热首字 118ms、LSP 精准注入——**同样的模型，体验上一个台阶**

## 边界：不是排他，是聚焦

- V1 只做 DeepSeek——把「问题解决工作台」这条链路（对话→授权→执行→交付）打磨到闭眼可用
- 架构上 ToolRegistry / Gateway 已抽象，未来加模型是「注册一个适配器」，不是推翻重来——但那不是 V1 的事
- 路线图公开在 [GitHub Issues](https://github.com/NinjaSln-labs/neonforge/issues?q=label%3Aroadmap)（label `roadmap` + Milestones）——多模型网关排在 V2
