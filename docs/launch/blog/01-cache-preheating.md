# 缓存预热：把 DeepSeek 首字延迟从 275ms 压到 118ms

## 问题：通用客户端的「慢」不是网络慢，是 KV 缓存没命中

用 DeepSeek 做 agent 的人都知道一个痛点：**每轮对话首字延迟不稳定**——同样的 prompt，有时 200ms 秒回，有时 2 秒起。差异不在模型算得快慢，而在**前缀是否命中服务端 KV 缓存**。

LLM 服务端的 KV cache 是**按前缀匹配**的：同一段前缀（system prompt + 工具定义 + 历史）第二次出现时，预计算的 KV 直接复用，跳过重复的 prefill。对 agent 应用这是决定性优化——因为 agent 的 system prompt 往往几千 token，而实际「新内容」只有最后一句用户输入。

**通用客户端的问题**：前缀不固定——每次拼接 system + 工具 + 历史，只要中间有任何顺序/换行差异，前缀就变了，KV 缓存永远打不中。

## 方案：确定性前缀 + 打开项目即预热

NeonForge 的做法分两步：

### 1. 前缀标准化（PrefixCache）

`buildStandardPrefix()` 把「agent 身份 + 工具定义 + 文件树摘要」拼成**字节级确定**的字符串：

- system 叙述（固定模板，无时间戳/无随机）
- 工具定义（固定顺序）
- 文件树摘要（最多 30 条，路径排序后截断——**不包含文件内容**，只含结构）
- 整体 sha256 hash 作为缓存键

文件树变了 → hash 变 → 前缀重建；没变 → 直接复用。Append-Only 缓存保留最近 20 个前缀版本——切项目/切文件不浪费。

### 2. 打开项目即预热（PreheatingService）

- 打开文件夹 → 构建前缀 → 后台发一个**最小成本预热请求**（v4-flash + thinking 关闭 + `max_tokens=1`，system 携带完整前缀 + 极简 user）
- 目的**不是拿答案**，是让服务端把这段前缀的 KV 算好、缓存住
- 状态机：`idle → preheating → ready / failed`，防并发（同前缀只预热一次），失败静默降级（不影响主流程）

## 实测数据（真实 DeepSeek API，2026-08）

| 场景 | 首字延迟 |
|------|---------|
| 冷启动（无缓存） | **275ms** |
| 预热后（KV 命中） | **118ms** |

提升 **57%**——达标产品指标（首字 ≤500ms，目标 300ms）。

## 为什么这值得写

1. **对用户**：打开项目就已经「热着」，说第一句话就有本地 IDE 般的响应感——不是「等它思考」，是「它早就准备好了」
2. **对成本**：预热请求 `max_tokens=1` 成本可忽略，换来每轮对话省一次 prefill
3. **对架构**：KV 缓存是服务端黑盒，但**前缀确定性**是客户端能控制的——这是 agent 应用少有人认真做的优化

## 局限与后续

- 预热只覆盖「打开项目」时刻；对话中途文件树变化会重建（hash 检测），重预热一次
- 首次预热有 200ms 左右成本（真实 API 冒烟实测）——换后续全程命中，值
- 打包版/弱网：预热失败自动降级，不阻塞对话
