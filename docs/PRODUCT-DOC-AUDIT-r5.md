## 四、问题

1. **[Major] 07 成功指标缺「确认交互质量」维度（#1）**
   - 现象：07 全文无「确认/授权/疲劳/方案卡/对账」任何指标落点；leading 表只有任务完成率/写入采用率（执行层）
   - 影响：三视角调研确认的核心风险「确认疲劳→橡皮图章→安全失效」与「决策点悬挂→模型乱动」（问题 A 类）在指标层**不可观测**——无法度量「用户被动背书模型自评」的恶化趋势；新设计（方案卡/证据对账/拒绝原因）的交互改进无量化验证手段
   - 建议（见五）
2. **[Minor] 北极星口径与「解决确认」语义未对齐（#2）**
   - 现象：北极星「每周完成写入的任务数」——完成=「改完写进文件」；领域 v4.0：交付≠解决（解决=证据对账确认）
   - 影响：指标度量执行而非解决——「写完了但没解决」的任务被计入北极星
   - 建议：leading 补「解决确认率」（证据对账通过/任务总数）
3. **[Minor] 07 反指标「自动写入不审核」口径与方案层审核的清单内自动放行需澄清（#3）**
   - 现象：反指标「任何为提升任务完成率而『自动写入不审核』的改动……禁止」；actionGate：方案确认后 plannedFiles 内 write 自动放行
   - 影响：语义不冲突（方案层审核完成后的自动 ≠ 不审核）但措辞会让实现期误读为「禁止清单内自动」
   - 建议：措辞明确「审核在方案层（方案卡）完成后的清单内自动放行不违反本反指标」
4. **[信息] 04 对齐索引未含新设计文档与 S 阶段实现序（#4）**
   - 现象：04 文档清单/工程实现顺序（旧 Phase 1-3）未引用 `intent-confirmation-domain-design.md`（scratch）与其 S0-S7
   - 影响：新实现者按 04 阅读序会漏设计文档（重构期必需）
   - 建议：04 补「重构期文档」引用（scratch 设计文档 + 审计报告）——scratch 不入 docs 索引的惯例可保持，但 04 应标注「重构期以 scratch 设计文档为权威」

## 五、建议

- #1：07 §2 leading 表补 3 项确认交互指标（Beta 起埋点）：
  - **授权卡滞留率**（授权请求→用户决策时长 >30s 占比——疲劳/悬挂代理；问题 A 复发监测）阈值建议 <20%
  - **方案修改率**（方案卡被修改/重出占比——意图对齐质量；过低=橡皮图章化、过高=方案质量差）建议区间 15-40%
  - **证据对账完成率**（解决确认前系统核验通过占比——证据机制生效度）建议 ≥70%
  - 反指标补 1 条：「不以机械确认速度为成功指标——确认决策时长缩短必须以『决策内容被审阅』为前提」
- #2：07 §2 补「解决确认率」leading（证据对账通过/任务总数，Beta 起）
- #3：07 §5 反指标措辞澄清（方案层审核后的清单内自动不违反）
- #4：04 补重构期文档引用（信息级）
- **权威裁决**：产品交互定义以 product/00（v2.2）为准；确认交互的实现语义以 A0 v4.0 + 意图确认设计文档为准；指标口径以 07（按 #1/#2/#3 修订后）为准
