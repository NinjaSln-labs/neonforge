- 相关：`docs/design/v1.0.0-s2-detailed-design.md` §5 冲突登记／§11 钩子（**本件承载其裁定，随动 v0.2**）；`docs/neonforgeV1.0.0/03-domain-tactics.md` §6 跨聚合一致性表「作用域修正」行＋§5 事件目录（**零改动**）；`docs/design/stage-specs/V1-S2-authorization-scope.md`（A4/A5/B2 判据面，**零改动**）；`docs/audits/stage5-s2-design-audit-2026-10-06.md`（异构审计 4.3 专项判＋发现 F-3/F-9）；ADR-026（铁律②／禁跨段）；ADR-029（上游签名正名先例＝「回上游改工件」的对照面）

## Context

S2 详设要把段3 §6「作用域修正」行落地。该行原文＝触发事件 `DecisionResolved(缘由=作用域修正)→ScopeAmended`、一致性策略「事件驱动（授权域内 Scope 消费决议）」、同事务范围「Scope 聚合＋timeline」、幂等「同 decisionPointId 只产一个版本」。

实现时发现一处上游留白：**修正后的新 entries 在事件面上没有载体**。`DecisionRaised`／`DecisionResolved` 的载荷键集受「禁增禁减」约束（段3 §5／S1 详设 §6 契约面），决议事件因此带不动一个 `ScopeEntry[]`；而「消费决议」若理解成订阅式，Scope 拿到的只有「某个修正决议已批准」这一事实，没有内容。三案摆在段5：

- **案 A（命令式消费）**：用户动作发 `scope:amend(delegationId, decisionPointId, entries)`，`Scope.amend(dp, entries, ts)` 把「决议在场∧缘由＝作用域修正∧值＝批准∧该决议未用过」四条当命令前置（I-17），事件仍由聚合草稿经 `TimelineRepo.append` 唯一机制口落账。
- **案 B（回段3 加载荷键）**：给 `DecisionResolved` 加 entries 键、改真订阅。＝铁律②第六次回退，动 22 事件闭集的载荷契约面，段3 出 v1.4 后须再派增量复审，并牵动 S1 已定稿的 payloadKeys 快照。
- **案 C（另设提案载体）**：决议之外新增「修正提案」实体或事件。＝引入新事实层，同样要过铁律②，且与「禁增禁减」裁定相撞。

异构审计（`mcode@MiniMax-M3`，非当前主同源）对该冲突做了独立判：(a) 根因**成立**（实测 `DecisionRaised`/`DecisionResolved` 键集确无 entries 位置）；(b) 详设所引「同族先例」**部分成立**——S1 的 `ipcDomain.ts` `decision:resolve` 处理器内 `markAwaitingUser()` 确是接线层 inline 命令、事实无误，但它同样与段3 §6「事件驱动（推进订阅）」的描述存在**形态偏差**，且 S1 出口审计未明示核查这一层；(c) 采案 A，案 B 代价过高，案 C 本阶段无实施路径。

用户据此裁：**案 A**。

## Decision

1. **段3 §6「作用域修正」行的「事件驱动」读法权威化**＝「授权域内 Scope **消费决议事实**」，不是「Scope 侧挂事件订阅器」。事件的产生与落账面不变：`Scope.amend` 返回 `ScopeAmended` 草稿，由 `TimelineRepo.append` 唯一机制口写入（S-1/I-2 不受影响），同事务范围仍是「Scope 聚合＋timeline」，幂等仍是「同 decisionPointId 只产一个版本」——该行的三个判据列在案 A 下逐条可测，**无一降级**。
2. **新 entries 的抵达路径＝用户命令**（`scope:amend`），不塞进事件载荷。批准权仅用户的事实由 `Scope.amend` 前置②（`resolution.value === '批准'`，拒绝/选项/未决一律拒）承载，与段2 X8「AI 可提请，批准权仅用户」一致。
3. **段3／段2／契约件／S1 详设全部零改动，铁律②回退次数＝0**。22 事件闭集、载荷键禁增禁减、`ScopeRepo` 两方法、高影响清单文案四项冻结面在案 A 下均不触碰。
4. **详设随动两处（v0.2）**：①§5 的「同族先例」补一句形态偏差声明——S1 的 inline 实现与段3 §6 该行描述本就同型偏差，S1 出口审计未判红；本件采同型，**不声称 S1 实现等于段3 描述**。②§11「本阶段新语义裁定＝无」改为「＝1 件，本 ADR」，F8 闸项填报口径随之引本件编号。
5. **案 B／案 C 的拒因留档**：案 B 用「措辞整齐」换「动上游事件契约面＋一轮增量复审＋S1 payloadKeys 快照重跑」，收益不抵代价；案 C 的提案载体是新事实层，V1 无第三个需要它的场景（S5 作废面消费的是决议，不是提案）。
6. **该读法可被 S5 复用**：卡滞催／弃（S5）同样落在「决议/事件事实 + 接线层命令消费」这套形态里；若 S5 出现必须真订阅的场景（证据域 `attachEvidenceCollector` 已是真订阅先例），回段5 重裁，不在段6 就地扩本件射程。

## Consequences

- 正面：S2 详设与段3 冻结件的冲突从「登记待裁」转为「已裁＋有据」；F-9 的 §5／§11 自相矛盾消除；段6 拿到的接口不再有「实现形态未定」这一悬点；22 事件契约面保持逐字不动，S1 已定稿的 `payloadKeys` 快照与表 N 追溯不必重跑。
- 负面/代价：①「事件驱动」一词在段3 §6 表内从此存在两种被接受的程度——「推进订阅」行与「Scope 消费决议」行按字面读会得到不同实现形态，下段读者须读本件才知道读法边界；②`scope:amend` 成为 S2 唯一新增写通道，UI 未给出提案面时用户得自己填 entries（呈现完整化属 S6，登记在详设 §11）；③案 A 的「同型先例」不如字面整洁，审计者明确要求详设不得把 S1 实现与段3 描述等同（已在 Decision 4① 落笔）。
- 后续：①`docs/design/v1.0.0-s2-detailed-design.md` 升 v0.2，§5/§11 随动＋其余精度项（F-4/F-6/F-7/F-11/F-13/F-14 等）同批修入；②修入后按「采纳修入必复审」派简单审计，只审增量面；③段5 出口闸 G 组的 ADR 同步项（F8）报本件编号；④S5 开工前核 Decision 6 的复用边界是否仍成立。
