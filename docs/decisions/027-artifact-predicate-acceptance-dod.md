## Context

1. 段3 §9 显式移交遗留账：「**产物谓词与 N3 OUT 判定**（"什么算有产物的委托"）移交段4——语言表 17 词中唯一无**战术判定落点**的词，段4 决定是否立 DoD 断言（如"收尾必有变更集类证据"）」。
2. 谓词在段2 已成词，缺的只是战术判据：段2 §4「产物（Artifact）」行＝「委托的最终交付物；**V1＝软件工程变更集＋其验证结果**；产物≠证据」。故本件不是造新语义，是给既有谓词补一个可执行判据。
3. 无判据的后果：段3 §8 `AcceptanceSpec` 只判「存在可打开核验且 Provenance＝系统采集的证据引用」，**不判证据类型**⇒ 一件只有命令输出/测试结果类证据、零变更集的委托也能通过验收收尾；段0 N3（无产物闲聊 OUT）与 G1（有明确产物）在 V1 无可执行判据，`docs/tests/coverage-matrix.md` 表 N 轴1/轴6 行悬空。
4. 用户 2026-10-05 裁定（段4 开工裁定批，所选选项文本已含「AcceptanceSpec 扩展＋L1 契约用例」）：**立 DoD**。

## Decision

1. **产物谓词 V1 的战术落点＝验收前置的证据类型判据**：待核验态委托必存在**至少一条 `EvidenceType`＝变更集**的证据引用，否则验收拒绝（`DelegationRejected` 路径可用：拒绝→原单重开）。产物≠证据的区分（段2 §4）保持不变——判据落在产物的**可核验记录**上，不新建 Artifact 聚合（段3 §2 已登记变更集不建聚合，本件不改）。
2. **承载方式＝`AcceptanceSpec` 谓词扩展，不新增不变量编号**：I-16 的编号、语义与违反时行为不变，其 Spec 内容按第 1 条细化。
3. **由此触发铁律②回退**：`AcceptanceSpec` 正文在段3 frozen 工件内 ⇒ 段3 增量修订 **v1.0→v1.1**（改动面＝§8 AcceptanceSpec 行、§4 I-16 行、§9 遗留账、**状态头（含标题版本号行、状态行、修订对照行、上游工件版本行四个子行**——v1.1 增量复审 M-01 要求逐子行登记，避免"登记面与实际面不精确重合"）），并按段2 v1.1 先例派**回补增量复审**（异构执行者，只审增量面），报告落 `docs/audits/stage3-domain-tactics-v1.1-increment-reaudit-2026-10-05.md`（文件名指针同时写入段3 状态头与修订对照行）。段4 不得在计划或 spec 内就地扩谓词（铁律②：不就地打补丁）。
4. **射程声明（有意取舍）**：与段0 裁定 B「先窄后宽」（V1 锚软件工程域）一致——纯调研/纯解释类委托在 V1 **无法收尾**。该取舍登记为射程外清单既有项「通用知识工作委托」（L0 §9）的正面佐证，不另开清单。
5. **实现阶段与渐进登记**：S4（证据核验域深化）负 DoD 主责；S1 骨架期 `AcceptanceSpec` 为薄实现（只判系统采集＋可打开核验），**S1 spec 边界节显式登记该缺口**，S4 收口；表 N 段7 列在 S4 前不得标绿（禁预先桩绿）。

6. **v1.2 补全（用户 t000088② 裁定，2026-10-05）——产物谓词「其验证结果」半边的战术落点**：EvidenceType 枚举扩增「验收判据运行结果」类（与现有「测试结果」语义有别：前者＝本委托 DoD 验收判据的运行产物，载荷指向 L1 vitest / L3 playwright 测试报告；后者＝通用测试输出）。AcceptanceSpec 加第二条合取条款：evidence 集合∃item.type=验收判据运行结果 ∧ delegationId=本委托。谓词本体不新立编号，与 Decision 1 共享 I-16（同条 Spec 两条独立合取条款，均为必要条件）。射程再次收紧：无验收判据运行结果证据的委托亦不可收尾。EvidenceType 枚举域由 3 值扩 4 值（变更集/命令输出/测试结果/验收判据运行结果），载荷键入 §5 EvidenceRecorded.type 字段（已存在，无事件闭集扩张）。**互斥标记规则**【v1.2，M-03】＝单值标记、不可同归两类；针对本委托 DoD 验收判据运行产出的报告一律记为「验收判据运行结果」而非「测试结果」（§3 EvidenceType VO 行＋§1 U6 同步登记；I-16 第二条款的前置）。实现侧产出约束归 S4 spec：① L1 验收判据运行结果写入机制（vitest 报告→EvidenceRecorded）；② L3 验收判据运行结果写入机制（playwright 报告→EvidenceRecorded）；③ 验收判据运行结果 evidence 与 delegationId 绑定的领域内约束。

## Consequences

- 正面：N3/G1 获得可执行判据；表 N 轴1（Job·先窄后宽）与轴6（能力边界）两行由 ⏳ 转为有承载；北极星证据闭环（L0 §1「每个'完成'可追溯到证据」）在类型面上收口——"有据"进一步收紧为"有**产物**据"。
- 负面/代价：段3 frozen 工件需一次增量修订＋一次增量复审（流程成本，先例已在段2 v1.1）；V1 无法收尾无变更集的委托（有意取舍，见 Decision 4）；S1 骨架期存在已登记的判据缺口（薄实现），须靠渐进登记纪律防"假绿"。
- **合取半边未落（v1.1 增量复审 M-02，登记为待用户裁定项）**：用户裁定文本＝「收尾必有**变更集类**证据」，本件据此只落段2「产物」合取谓词（变更集＋**其验证结果**）的变更集半边。「其验证结果」半边在 V1 无判据落点——`EvidenceType∈{测试结果, 命令输出}` 存在与否不影响 `AcceptanceSpec` 结果，I-5 判"系统采集"非"验证结果存在"，不构成等价兜底。补全该半边＝再一次收紧验收（无验证证据的委托亦不可收尾），属**射程语义**，须用户裁定而非段4 自裁 ⇒ 段3 §9 遗留账措辞由「已全数关闭」改为「**部分关闭**」，§8 增「合取半边登记」。未裁前下游不得就地补全、亦不得宣称已覆盖（铁律①／②）。
