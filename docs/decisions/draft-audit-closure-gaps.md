# 审计闭环缺口：成熟方案对比与本仓设计（2026-10-07）

> 目的：回答「改完就以为结案」这一反复出现的失效，落**针对本仓**的结论与**可被 agent 遵守**的设计。
> 触发：用户 2026-10-07 连问两轮——①「很多次再次改完后没审计，根因是什么」②「改过以后忘记审计」；并追加「刚才那次不是设计文档相关的吗」。
> 本文是**调研＋设计结论**，不是 ADR；是否立 ADR／补门禁待用户裁。

## 0. 两处实证（本会话，非假想）

| # | 事实 | 性质 |
|---|---|---|
| 实证-1 | S3 两轮段5 出口审计各修 finding（契约件 7 条、详设 17 条）后，**都未复跑该切片闸**就继续；用户指出才补派窄单（24/24 PASS）。 | **改「被审对象」→ 结论失效，靠人记得** |
| 实证-2 | `55e162a` 我**手改两份审计报告**（订正计数笔误 15→17＋追加复验段）。改动**实质无害**（零 finding 状态变更、有复验单独立依据），但**无任何门禁能看见这次对审计记录的改写**。 | **改「审计记录」→ 凭证可被静默改写** |

**根因（三条，缺一即复发）：**
1. **缺「修 → 复审」的强制回路**：ADR-032 有「修入后复跑」条文，但它是**纪律**不是**流程步骤**——执行者的状态机是「出件→审计→采纳→修→下一步」，没把「修」当产生新状态的动作。
2. **审计结论不绑对象版本**：报告没有「对应工件＝commit X」的绑定；工件变了，报告仍挂着像有效。
3. **改稿者兼任判定者**：修 finding 与判「修好没」是同一双手（ADR-032 要的恰是改稿者≠判定者），且只在被点名时才派复验。

## 1. 成熟方案对比（工业界→原则）

| 成熟机制 | 它防的失效 | 本仓现状 |
|---|---|---|
| GitHub *Dismiss stale approvals on new commits*／GitLab *Remove all approvals when commits added*（默认开）／Phabricator *Accepted Prior Diff*／Gerrit patch-set `copyCondition` 使旧票 `outdated` | 审查对象变了，旧批准自动作废 | **靠人记得**（实证-1） |
| GitHub required checks 绑 **commit SHA**（旧 SHA 通过不算数）；Gerrit 票绑 patch set | 结论绑「最新版/分支」而非不可变制品 | 报告**未绑工件版本**（根因-2） |
| GitLab `patch-id`／GitHub diff-state／Bitbucket 新 merge condition | 判定「是否变化」按**净 diff**，不误伤无变化 | 无（无所谓） |
| GitHub merge queue / Bors / Zuul 在**真实合并结果**上重跑 | 旧基线结论作废 | 不适用（单链） |
| GitLab *Prevent approval by creator*；Google「someone other than the author」＋LGTM；Fagan Author≠Inspector | 改稿者不得当判定者 | ADR-032 有，但**未机械化**（根因-3） |
| TDD 红-绿；*prove the test can fail* | 测试须先在未修代码上红过 | 已有（缺「红证据入档」） |
| 21 CFR 820.100(a)(4)／ISO 13485 §8.5.2 **有效性验证**；correction ≠ corrective action | 「已实施」不等于「问题解决」 | 有复跑，无「有效性」关 |
| Gerrit `allowPostSubmit`：「事后补票只能是记录，不能追溯把『未验证』改写成『已验证』」 | 凭证不可静默改写 | **裸奔**（实证-2） |
| Automation bias（Lyell & Coiera 2017）：**「加强要求」类干预几乎无效；降低认知负荷才有效** | 工具绿灯被当充分证据 | 关键依据：**口号式条文无效**，须机械化 |
| Checklist fatigue（Grigg 2015）：复核退化为打卡 | 清单勾完≠判断发生 | 同上 |

**归纳为一条主轴**：**任何使审查对象变化的动作，必须使此前结论自动失效；且「失效—重验」要么机器可判，要么在流程必经点上无法绕过。** 靠 prose 纪律（如现有 ADR-032 的「修入后复跑」）已被证明会漂移。

## 2. 本仓可用的「强制载体」（agent 必经，非 prose）

调研结论「降低认知负荷／机械化才有效」→ 落到本仓，agent 的**工作流必经点**只有三个，门禁必须挂在这里：

| 载体 | agent 何时必经 | 成熟度 | 挂什么 |
|---|---|---|---|
| **`.handoff/` CLI 门禁**（`handoff.py check`，已有 16 维判据 + `writes.jsonl` 哈希凭证） | 每次交接／`check`／`close` | **现成、已机械化**（`writes.jsonl` 已对每文件记 sha＋ns-mtime，手改即抓） | 「待复验」待办 ＋ 「审计记录哈希对账」 |
| **git hook**（lefthook pre-commit／`.githooks/`） | 每次 commit | 现成（desens 已挂） | commit 触碰被审工件／审计报告时的**提示或拦** |
| **`pipeline-0to1` 技能拦截条件** | 每次段推进／放行判定 | 现成（技能软链本仓） | 段6：「finding 未复验 → 不许进出口闸」（已有近义条，需落实为**可判**） |

**设计原则**：**机械化到「不记得也过不去」**，而不是再加一条散文纪律。Automation bias 研究明说「加强要求／训练／反馈」几乎无效，所以**不采用**「在 AGENTS.md 里多写一句」这种方案。

## 3. 设计（三件，按「可机械化程度」排序）

### 件 A：审计记录写入走**哈希凭证对账**（最硬，直接复用现成机制）
- **机制**：把 `docs/audits/**` ＋ `docs/reviews/**` 纳入凭证明细——每次经「登记动作」记 sha；其后任何手改 ⇒ 对账红。
- **落点**：**两选一**——(a) 扩 `handoff.py` 的 `writes.jsonl` 覆盖面（但它现只纳管 `.handoff/` 内文件，扩到 `docs/` 是改技能库件、跨仓影响，须评估）；(b) **新建仓内 `tools/audit-ledger.py`**（本仓自持，照抄 `writes.jsonl` 的 `{sha, mt}` 形，`check` 挂一判据）。**推荐 (b)**——不碰通用技能库件、本仓可独立演进。
- **防**：实证-2（改报告无痕）。**改审计报告必须重新登记并说明理由**——把「手改凭证」变成「留痕动作」。
- **成本**：低（照抄 `writes.jsonl` 既有实现，`tools/` 下新脚本 ＋ `check` 挂钩）。

### 件 B：审计结论**绑工件版本**，偏离即自动标「已过时」
- **机制**：审计报告头部加**强制字段** `被审工件@commit`（如 `V1-S3-persistence-recovery.md@c6e024e`）；`check`／门禁机械比对「报告记的 commit」vs「工件当前 commit」——不等 ⇒ 报告标 `STALE`、`check` 红。
- **落点**：报告模板 ＋ 一个对账判据。
- **防**：根因-2（报告说旧版本）。**这直接命中实证-1**：工件一动，报告即失效，无法「挂着像有效」。
- **成本**：低-中（需给报告头部定字段形 + 比对逻辑）。

### 件 C：「修 → 复验」机械化为一等状态
- **机制**：把 ADR-032 的「修入后复跑」从散文落成 **handoff action**——任何 finding 修入 = 开一条 `action`（`[高] 复验 <工件> @<新commit>`，`blockedBy` 指向原审计报告 id）；**未 `close` 该 action，段6 拦截条件即成立**（`pipeline-0to1` 已有「finding 未处置 → 不许进出口闸」条，把「处置」精确到「复验 close」）。
- **落点**：handoff 用法纪律（写进 ADR）＋ pipeline 技能拦截条微调（已有近义条）。
- **防**：根因-1/3（靠记得／自判自修）。
- **成本**：低（handoff CLI 现成，无需新代码）。

### 件 D（可选，最软）：git pre-commit **提示**触碰被审工件
- 当一次 commit 改了「已登记审计报告的工件」而没动对应报告 ⇒ 提示（不拦）。
- 成本低但效力弱（提示会被忽略，checklist fatigue）——**列为次选**，A/B/C 已是机器可判，D 仅作辅助。

## 4. 「怎么让 agent 遵守」——正面回答

用户的核心关切。**唯一被研究支持有效的做法是「机械化到必经点」，不是「写清纪律」。** 具体三条：

1. **能机器判的，就别写成纪律**：件 A/B 是「不记得也过不去」（`check` 红）。
2. **不能机器判的，挂到已有必经门禁**：件 C 用 handoff action——agent 每次交接必跑 `check`，未 close 的复验 action 会让 `next` 非空且拦截条件成立。
3. **绝不再加「请记得…」型条文**：Automation bias 综述（JAMIA 2017）明言此类干预「几乎没有效果」。现有 ADR-032 第 5 条「修入后复跑」正是此类条文，**它已被实证-1 证伪**——本次设计就是把它从 prose 升级为机制。

**验收判据（本设计成立的标准）**：把实证-1／实证-2 的场景重演一遍，**不靠任何人记得**，`check` 就报红。做不到这条，设计即失败。

## 5. 待用户裁

1. 是否采纳件 A／B／C（D 次选）？
2. 落到哪：**新 ADR**（如 ADR-035「审计闭环失效与重验门禁」）＋ 改 `handoff.py`／新增 `tools/audit-ledger.py`？
3. 范围：本次只做**件 B**（最低成本、直接命中实证-1），还是一次做 A+B+C？

**建议**：**B 先行**（低成本、命中最高频的实证-1），A/C 同批评估；D 不做。理由＝先堵最常复发的口，且 B 不依赖改 handoff.py 内部。
